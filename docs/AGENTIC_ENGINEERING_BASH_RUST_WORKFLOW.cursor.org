* Purpose

This document formalizes the *agentic engineering workflow* for this repository: use *Bash (or scripting) first* for quick prototyping and ideation, then *formalize in Rust* for production-quality code. It is intended for AI coding agents (Codex, Claude, Gemini, Kimi, GLM, etc.) and human engineers driving them.

The second half of this document is *model- and area-specific*: for each supported model and each workflow area (Bash prototyping, contract writing, Rust porting, testing, debugging), we give detailed context, prompt templates, pitfalls, and “done” criteria.

* The ideal workflow (summary)

** Phase 1 — Prototype / ideation (Bash)
- Implement in Bash/scripts first. Document behavior. Define contract (options, paths, exit codes). No Rust yet.

** Phase 2 — Contract freeze
- Write or update the single source of truth. No Rust port until the contract exists.

** Phase 3 — Production formalization (Rust)
- Implement to the contract only. Add parity tests. Use repo patterns. Optional: CI comparing Bash vs Rust.

** Phase 4 — Ongoing
- New behavior always starts in Bash; port to Rust when that area is stable.

* Workflow areas (what agents do)

We define five *areas* that agents operate in. Each model section later tailors how to work in each area.

** Area 1 — Bash prototyping

| Sub-area        | Location / surface              | Examples |
|-----------------+---------------------------------+----------|
| Launcher options| =container/launch_container.sh=  | New =--flag=, new env var, new mount |
| Entrypoints     | =container/entrypoints/*.sh=    | New script, new behavior in default/run-job |
| Tools           | =tools/zephyr_*=, =bin/sygaldry=| New subcommand, new script |
| Pipeline steps  | =tools/zephyr_stage_spack.sh=    | New step, new exit code, new option |

- *Output*: Working Bash that does the thing; a short note (or inline comment) on options, paths, exit codes.
- *Do not*: Add Rust; optimize for speed; introduce new languages.

** Area 2 — Contract / spec writing

| Sub-area     | Artifact / location                    | Content |
|--------------+----------------------------------------+--------|
| Infra contract | =container/ZEPHYR_SYSTEM_DESIGN.md=  | Paths, layout, env vars, entrypoint names |
| Feature spec | Same doc or =CONTRACT.md= / =docs/=   | New option semantics, exit codes, file formats |
| CLI surface  | Contract + =cli.rs= (later)            | Subcommands, args, global flags |

- *Output*: Written spec that Rust will implement. No ambiguity on: when is X set? what path? what exit code on failure?
- *Rule*: No Rust port starts until the contract for that feature is written.

** Area 3 — Rust porting

| Sub-area       | Rust location                    | Responsibility |
|----------------+----------------------------------+----------------|
| Host launch    | =crates/zephyr/src/host/=        | launcher, docker_args, dirs, image, lease, requirements, cuda |
| Host jobs      | =host/job.rs=, =host/staging.rs= | Job run/status/tail; staging pipeline |
| Container init | =crates/zephyr/src/container/=   | spack, cuda, mlsys_venv, entrypoint |
| Container actions | =container/*.rs=              | gpu_check, verify, uv_install, hf_download |
| CLI            | =cli.rs=, =config.rs=, =main.rs= | Subcommands, config from env, dispatch |
| Errors & paths | =error.rs=, =paths.rs=           | ZephyrError variants, HostLayout, container paths |

- *Output*: Rust code that satisfies the contract; new or updated tests.
- *Rule*: Match contract exactly; use =thiserror=, =clap=, existing =HostLayout= / =ZephyrConfig=.

** Area 4 — Testing and parity

| Sub-area        | What to do |
|-----------------+------------|
| Unit tests      | Rust: =#[test]= in the same module or =tests/=; assert contract (e.g. argv build, exit code). |
| Integration     | Run Bash launcher and Rust launcher with same env; compare =docker run= argv or config output. |
| Staging         | Same =--spec= / =--run-root=; compare exit codes and that both run the same steps. |
| Job contract    | Job started by Bash vs Rust: same status path, same JSONL shape; status/tail work for both. |

- *Output*: Tests in repo; optional CI job that compares Bash vs Rust for a fixed scenario.

** Area 5 — Debugging and drift

| Situation           | What to do |
|---------------------+------------|
| Bug in Bash only    | Fix in Bash; if part of contract, update contract and then fix Rust if it has that surface. |
| Bug in Rust only    | Fix in Rust; contract is the spec. |
| Bash and Rust differ| Treat contract as truth; fix the side that deviates; if contract is wrong, fix contract first, then both impls. |
| New env var / path  | Add to contract; add in Bash; port to Rust; add to =paths.rs= or =config.rs= and to Bash. |

- *Output*: Both sides aligned with the contract; contract doc updated when semantics change.

* Universal agent instructions (any model)

** When adding a new feature
1. Implement in Bash first (Area 1). Prefer =container/=, =tools/=, =bin/sygaldry=.
2. Document the contract (Area 2). Put it in =ZEPHYR_SYSTEM_DESIGN.md= or =CONTRACT.md=.
3. Do not add Rust until step 2 is done and behavior is stable.
4. Port to Rust (Area 3); add tests (Area 4) that assert parity where feasible.

** When fixing a bug
- Bash-only: fix in Bash; update contract if needed; then fix Rust if it implements that surface.
- Rust-only: fix in Rust.
- Both: fix in both, or fix in Bash and port the fix to Rust; contract is the reference.

** When refactoring
- Prefer refactors that clarify the contract (e.g. single list of volumes). Do not refactor Bash and Rust in one change unless it is a mechanical port.

* Model-specific tailoring (detailed)

** Codex (OpenAI / Cursor code models)

*** Profile
- *Strength*: Fast code generation; good at following file/structure context; strong on syntax.
- *Weakness*: Can invent env names or paths; may skip contract checks; sometimes merges multiple steps into one.
- *Context*: Works best with explicit file paths and one clear task per turn. Keep context window focused on the files being edited.

*** Area 1 — Bash prototyping (Codex)

- *Context to attach*:
  - The exact file(s) to edit: =container/launch_container.sh=, or =container/entrypoints/run-job.sh=, etc.
  - The relevant section (e.g. “the =main()= function”, “the =build_docker_args= function”).
  - One or two sentences from =ZEPHYR_SYSTEM_DESIGN.md= or =CONTRACT.md= that define the intended behavior, if it already exists.
- *Prompt shape*: One task per message. Examples:
  - “In =container/launch_container.sh=, add support for =--cache-profile=<value>=. Allowed values: shared, isolated, hybrid. Default: shared. Store in a variable and pass it into =build_docker_args=.”
  - “In =container/entrypoints/default.sh=, after Spack init, if =SYGALDRY_SKIP_GPU_CHECK= is set, skip the GPU check and go straight to the shell.”
- *Chunking*: If the feature needs several edits (e.g. add variable, add case in switch, add mount in =build_docker_args=), do one edit per turn and say “Next, add the same option to =build_docker_args= so it is passed as an env var into the container.”
- *Done*: Script runs and does the new thing; you have a one-line note: “Contract: --cache-profile= shared|isolated|hybrid, default shared; env SYGALDRY_CACHE_PROFILE.”

*** Area 2 — Contract writing (Codex)

- *Context to attach*:
  - =container/ZEPHYR_SYSTEM_DESIGN.md= (full or the “Contract” / “Paths” section).
  - The Bash change you just made (diff or short description).
- *Prompt shape*:
  - “We added =--cache-profile= to the launcher. Add a subsection to ZEPHYR_SYSTEM_DESIGN.md (or CONTRACT.md) that specifies: option name, allowed values, default, env var name, and how it affects mounts (one sentence per profile).”
- *Chunking*: One subsection per message. If the contract is long, ask for “only the subsection for cache profile” first, then “add the subsection for the new entrypoint X”.
- *Done*: Contract doc contains unambiguous spec for the new behavior; a Rust implementer could implement from that doc alone.

*** Area 3 — Rust porting (Codex)

- *Context to attach*:
  - The contract subsection for the feature.
  - The exact Bash code that implements it (one function or one block).
  - The Rust files to touch: e.g. =crates/zephyr/src/config.rs=, =host/docker_args.rs=, =cli.rs=.
  - One existing similar feature in Rust (e.g. “=lease_mode= is similar; see how it is in =config.rs= and =docker_args.rs=”).
- *Prompt shape*: One module or one concern per turn.
  - “In =config.rs=, add =cache_profile= to =ZephyrConfig= and =CliOverrides=. Allowed values: shared, isolated, hybrid. Default shared. Use the same env var as in the contract.”
  - “In =host/docker_args.rs=, use =config.cache_profile= to choose which cache paths to mount. Follow the contract table for each profile.”
- *Chunking*: Do not ask for “port the whole feature” in one go. Order: config and CLI → docker_args (or relevant host module) → container if needed → tests.
- *Done*: Rust builds; new code follows existing patterns (=env_chain=, =CliOverrides=, =HostLayout=); no behavior beyond the contract.

*** Area 4 — Testing (Codex)

- *Context to attach*:
  - The contract for the feature.
  - =crates/zephyr/src/host/docker_args.rs= (or the module under test) and existing =#[test]= in that file.
- *Prompt shape*:
  - “Add a test that builds docker args with =cache_profile= isolated and checks that the volume list includes the isolated cache path from =HostLayout=.”
  - “Add a test that when =--cache-profile= invalid= is passed, we get an error (or clap rejects it).”
- *Chunking*: One test or one test file per message.
- *Done*: =cargo test= passes; the new tests assert contract (paths, presence/absence of flags).

*** Area 5 — Debugging / drift (Codex)

- *Context to attach*: The contract; the Bash code; the Rust code; the observed difference (e.g. “Bash passes =X=, Rust does not”).
- *Prompt shape*:
  - “Contract says X. In =launch_container.sh= we do Y. In =docker_args.rs= we do Z. Which is wrong? Fix the one that does not match the contract.”
- *Done*: Both sides match the contract; contract updated if the intended behavior was wrong.

*** Codex — Pitfalls and mitigations

| Pitfall | Mitigation |
|---------+------------|
| Invents =SYGALDRY_FOO= or =/opt/foo= | Always supply =paths.rs= or contract path table; say “use only paths from paths.rs / contract”. |
| Skips error handling | Ask explicitly: “If the user passes an invalid value, what should happen? Add that check.” |
| One big “port everything” | Break into: “add type”, “add field”, “add logic”, “add test”. |
| Forgets to export env in container | Remind: “The container must see this; add it to the env list in =build_docker_args= (Bash) and =docker_args::build= (Rust).” |

** Claude (Opus / Sonnet)

*** Profile
- *Strength*: Long context; strong at docs and structured reasoning; can hold contract + Bash + Rust in one conversation; good at “port this and explain”.
- *Weakness*: May over-abstract or add “nice” behavior not in the contract; sometimes verbose.

*** Area 1 — Bash prototyping (Claude Opus/Sonnet)

- *Context to attach*:
  - Full =container/launch_container.sh= or the script you are extending (if under ~600 lines); or the relevant entrypoint and =container/lib/spack_init.sh=.
  - =container/ZEPHYR_SYSTEM_DESIGN.md= or the “Contract” section so behavior stays on-contract.
  - This workflow doc (or the “Ideal workflow” and “Area 1” sections).
- *Prompt shape* (can be larger):
  - “We need to support =--repo <path>= for multi-repo mode. In =launch_container.sh=: (1) parse =--repo= and resolve to absolute path. (2) In =build_docker_args=, when repo is set, add mounts for sygaldry at /opt/sygaldry (ro), workspace at /workspace, and repo at /workspace/<basename>. Workdir = /workspace/<basename>. (3) Set =SYGALDRY_ROOT= in the container to that workdir. Implement this to match ZEPHYR_SYSTEM_DESIGN.md multi-repo section.”
  - “Add a new entrypoint =my-tool.sh= that: sources spack_init, runs =my-tool= with args. Put it in =container/entrypoints/= and document in the contract.”
- *Chunking*: Can do one feature (one flag or one entrypoint) in one turn if the spec is clear. For “add a whole new pipeline step”, do one step per turn.
- *Done*: Bash implements the described behavior; you have a short contract snippet (or the agent proposes one).

*** Area 2 — Contract writing (Claude Opus/Sonnet)

- *Context to attach*:
  - Full =ZEPHYR_SYSTEM_DESIGN.md= (or CONTRACT.md).
  - The Bash implementation (diff or summary) and any existing informal notes.
- *Prompt shape*:
  - “We implemented multi-repo mode in Bash. Draft the formal contract subsection: option name, semantics, paths, env vars, and any error conditions. Write it so a Rust developer can implement from this alone. Insert it into ZEPHYR_SYSTEM_DESIGN.md under a ‘Multi-repo mode’ heading.”
  - “Review the new entrypoint =my-tool.sh=. Add a row to the contract’s entrypoint table: name, purpose, args, and which env vars it reads.”
- *Chunking*: Can draft a full subsection in one go. If the doc is large, ask for “only the new subsection” and then “insert it after section X”.
- *Done*: Contract is unambiguous and complete for the new behavior; no “TBD” or “same as Bash”.

*** Area 3 — Rust porting (Claude Opus/Sonnet)

- *Context to attach*:
  - The contract for the feature (full subsection).
  - The Bash code that implements it (relevant functions or blocks).
  - =crates/zephyr/src/= structure: =config.rs=, =host/mod.rs=, =host/docker_args.rs=, =host/launcher.rs=, =error.rs=, =paths.rs= (key types and functions).
- *Prompt shape*:
  - “Port the multi-repo behavior from =launch_container.sh= (attach the repo/mount/workdir logic) to Rust. Contract: [paste]. Requirements: (1) Add =LaunchMode= and repo path to config; (2) In =docker_args.rs=, =build_mode_mounts= should match the contract; (3) Use =ZephyrError= with =WithHint= for errors; (4) Add unit tests that assert the mount list for multi-repo matches the contract. Do not add behavior beyond the contract.”
  - “Port the =--cache-profile= logic from Bash to Rust. Follow existing =lease_mode= and =BuildPolicy= patterns in =config.rs= and =docker_args.rs=.”
- *Chunking*: Can do one feature (e.g. multi-repo, or cache profile) in one turn. For a large feature, break into “config + CLI”, “docker_args”, “tests”.
- *Done*: Rust compiles and tests pass; behavior matches contract; errors use =WithHint= where helpful; no extra features.

*** Area 4 — Testing (Claude Opus/Sonnet)

- *Context to attach*: Contract; Rust module under test; existing tests in that module or in =tests/=.
- *Prompt shape*:
  - “Add integration tests for docker args: for the same =ZephyrConfig= (e.g. project_id=test, repo=/tmp/repo, cache_profile=isolated), compare the list of =--volume= and =--env= produced by our =docker_args::build= with the contract. Prefer a test that builds config, calls =build=, and asserts on the presence and value of key args.”
  - “Add a test that runs the staging pipeline with =--spec py-foo= and asserts exit code 0 and that the view contains the new package. If that is too heavy, add a unit test that mocks the steps and asserts the exit code mapping from the contract.”
- *Done*: New tests are in the repo and pass; they assert contract (paths, env, exit codes, or argv shape).

*** Area 5 — Debugging / drift (Claude Opus/Sonnet)

- *Context to attach*: Contract; Bash code; Rust code; description of the mismatch (e.g. “Bash sets X, Rust sets Y” or “status file path differs”).
- *Prompt shape*:
  - “Contract says [paste]. Bash does A. Rust does B. User sees [symptom]. Which implementation is wrong? Propose a fix for the wrong side and, if needed, a one-line contract fix.”
  - “We added a new mount in Bash but not in Rust. List the exact =--volume= we need to add in =docker_args.rs= to match the contract and the Bash =build_docker_args=.”
- *Done*: One side (or the contract) is fixed so both sides match; no behavior change beyond fixing the bug.

*** Claude Opus/Sonnet — Pitfalls and mitigations

| Pitfall | Mitigation |
|---------+------------|
| Over-abstracting (traits, generics) | “Match the contract exactly; do not introduce new abstractions. Follow the style of =host/launcher.rs=.” |
| Adding “helpful” behavior | “Do not add features not in the contract. If you think something is missing, list it and we will update the contract first.” |
| Long prose in code comments | Prefer short comments; point to contract: “See ZEPHYR_SYSTEM_DESIGN.md § X.” |
| Contract and code drift | After Rust port, ask: “List every assumption in the Rust code that is not explicitly in the contract.” |

** Claude (Haiku / smaller / fast)

*** Profile
- *Strength*: Fast, cheap; good for small, localized edits; follows line-level instructions.
- *Weakness*: Shorter effective context; may drop parts of a multi-step request.

*** Area 1 — Bash prototyping (Claude Haiku)

- *Context to attach*: Only the file(s) you are editing and the exact lines (e.g. “lines 350–400 of launch_container.sh”). Keep under ~300 lines of context if possible.
- *Prompt shape*: One change per message.
  - “In =container/launch_container.sh=, in the =main()= while loop that parses args, add a case for =--run-id= and =--run-id=*) that sets =run_id=.”
  - “In =build_docker_args=, add =--env=SYGALDRY_RUN_ID=${_cfg[run_id]}= to the docker_args list.”
- *Chunking*: One function or one case block per turn. If you need three edits, do three messages: “Add the variable”, “Add the case”, “Add the env var”.
- *Done*: The single requested edit is done; run the script manually to confirm.

*** Area 2 — Contract writing (Claude Haiku)

- *Context to attach*: The specific section of =ZEPHYR_SYSTEM_DESIGN.md= where the new content goes (e.g. “the ‘Launcher options’ table”) and the Bash change (one paragraph summary).
- *Prompt shape*:
  - “Add one row to the Launcher options table: option =--run-id=, env =SYGALDRY_RUN_ID=, default =run-<date>-<pid>=, purpose = tracing and lease identity.”
- *Done*: One table row or one short paragraph added; no full-page draft.

*** Area 3 — Rust porting (Claude Haiku)

- *Context to attach*: One Rust file (e.g. =config.rs= or =host/docker_args.rs=) and the exact Bash snippet (10–30 lines) that implements the behavior.
- *Prompt shape*:
  - “In =config.rs=, add =run_id: Option<String>= to =CliOverrides= and resolve it in =ZephyrConfig::from_env=: if set, use it; else default =run-<timestamp>-<pid>. Use the same format as in launch_container.sh (see attached Bash).”
  - “In =host/docker_args.rs=, add =SYGALDRY_RUN_ID= to the env list when =config.run_id= is set. See ENV_PASSTHROUGH or the existing env block.”
- *Chunking*: One struct field, one function, or one block per turn.
- *Done*: The single requested Rust change is done; =cargo build= passes.

*** Area 4 — Testing (Claude Haiku)

- *Context to attach*: The one test file or one =#[test]= block you are extending.
- *Prompt shape*:
  - “In =crates/zephyr/src/cli.rs=, add a test =parse_run_id= that parses =--run-id myrun= and asserts =cli.run_id == Some(\"myrun\")=.”
- *Done*: One test added; =cargo test parse_run_id= passes.

*** Area 5 — Debugging (Claude Haiku)

- *Context to attach*: The single file and the single wrong behavior (e.g. “line 120 in docker_args.rs: we use =foo= but contract says =bar=”).
- *Prompt shape*: “In =docker_args.rs= line 120, the contract says the env var should be =SYGALDRY_RUN_ID=. Change =RUN_ID= to =SYGALDRY_RUN_ID=.”
- *Done*: The one fix applied; re-run tests.

*** Claude Haiku — Pitfalls and mitigations

| Pitfall | Mitigation |
|---------+------------|
| Drops one of several steps | Send one step per message; confirm “done” before “next step”. |
| Loses track of contract | Re-attach the one sentence from the contract that applies to this edit. |
| Edits the wrong file | Always name the file and, if possible, the function or line range. |

** Gemini (Google)

*** Profile
- *Strength*: Reasoning; code explanation; multi-step planning; can propose a “parity checklist” before coding.
- *Weakness*: Sometimes verbose or repetitive; may need a nudge to match repo style.

*** Area 1 — Bash prototyping (Gemini)

- *Context to attach*:
  - =container/launch_container.sh= (or the script) and =ZEPHYR_SYSTEM_DESIGN.md= contract section.
  - This workflow doc (“Area 1” and “Ideal workflow”).
- *Prompt shape*:
  - “We want to add =--lease-mode= off|warn|enforce. First, list the exact changes needed: (1) where to parse the flag, (2) where to pass it to the lease logic, (3) what env var to set in the container. Then implement those changes in =launch_container.sh=.”
  - “Before writing code: what should the contract say for =--lease-mode=? Draft the contract bullet points, then implement in Bash to match.”
- *Chunking*: Can do “plan then implement” in one turn, or “draft contract then implement” in two turns.
- *Done*: You have a short plan or contract snippet and Bash that matches it.

*** Area 2 — Contract writing (Gemini)

- *Context to attach*: Full contract doc; the Bash implementation (summary or diff).
- *Prompt shape*:
  - “We added lease mode. Draft the contract: option name, allowed values, default, semantics for each value (off/warn/enforce), and where the lease file is stored. Write it so that a Rust developer can implement without reading the Bash.”
  - “Review the entrypoint =verify-gpu.sh=. Produce a contract entry: name, purpose, inputs (env vars), outputs (exit code, stdout/stderr), and any side effects.”
- *Done*: Contract subsection is complete and implementation-independent.

*** Area 3 — Rust porting (Gemini)

- *Context to attach*: Contract for the feature; Bash implementation; =crates/zephyr/src/= (key modules).
- *Prompt shape*:
  - “Before writing Rust: list a parity checklist—for this feature, what must be true for Bash and Rust to be equivalent? (e.g. same env var name, same lease file path, same exit codes.) Then implement the Rust side to satisfy that checklist.”
  - “Port the lease logic from Bash (attach =acquire_lease= and =release_lease=) to Rust. Requirements: (1) Same file format and path; (2) RAII guard for release; (3) Same LeaseMode semantics. Match the style of =host/lease.rs= and =error.rs=.”
- *Chunking*: “Checklist then implement” works well. For large ports, “checklist” → “config + types” → “host logic” → “tests”.
- *Done*: Parity checklist exists; Rust implements it; tests cover the checklist items.

*** Area 4 — Testing (Gemini)

- *Context to attach*: Parity checklist; Rust code; existing tests.
- *Prompt shape*:
  - “Turn the parity checklist into test names and assertions. For each checklist item, add a test that asserts it (e.g. ‘lease file path matches contract’ → test that =lease_file_for= returns the path from =HostLayout=).”
  - “Add an integration test: run Bash launcher with env X and Rust launcher with same config; diff the =docker run= argv (or the =-v= and =-e= lines). Skip if too heavy; otherwise use a helper script.”
- *Done*: Tests exist that map to the parity checklist; they pass.

*** Area 5 — Debugging (Gemini)

- *Context to attach*: Contract; both implementations; the observed discrepancy.
- *Prompt shape*:
  - “Contract says A. Bash does B. Rust does C. Which of B or C is wrong? Propose a fix and update the contract if the intended behavior was unclear.”
  - “Generate a short parity checklist for ‘job status file path’. Then verify Bash and Rust both satisfy it; if not, fix the one that doesn’t.”
- *Done*: Clear answer (which side was wrong); fix applied; contract updated if needed.

*** Gemini — Pitfalls and mitigations

| Pitfall | Mitigation |
|---------+------------|
| Verbose or repetitive code | “Match the repo style. See =host/launcher.rs= for length and structure. Remove redundancy.” |
| Checklist too vague | Ask for “concrete checklist: exact env var names, exact paths, exact exit codes from the contract.” |
| Explains instead of coding | “Implement the changes now; keep comments to one line per block.” |

** Kimi (Moonshot / Kimi)

*** Profile
- *Strength*: Long context; can hold full workflow + contract; Chinese-friendly if the codebase has Chinese comments.
- *Weakness*: May assume path or env names; insist on repo constants.

*** Area 1 — Bash prototyping (Kimi)

- *Context to attach*:
  - This full workflow doc (or at least “Ideal workflow”, “Area 1”, “Area 2”).
  - =container/ZEPHYR_SYSTEM_DESIGN.md= (or the relevant contract section).
  - The script to extend: =container/launch_container.sh= or =container/entrypoints/run-job.sh=.
- *Prompt shape*:
  - “Following the bash-first workflow: implement [feature X] in Bash. Use only paths and env var names from ZEPHYR_SYSTEM_DESIGN.md. After implementing, list the contract bullets you would add (option name, default, paths, exit codes).”
  - “Add a new entrypoint =my-entrypoint.sh= that sources spack_init and runs =my-tool= with args. Document the entrypoint in the contract style (name, purpose, args).”
- *Chunking*: Can do one feature in one turn if the contract section is in context. For large features, “implement in Bash” first turn, “list contract bullets” second turn.
- *Done*: Bash works; you have an explicit list of contract bullets to add.

*** Area 2 — Contract writing (Kimi)

- *Context to attach*: =ZEPHYR_SYSTEM_DESIGN.md=; the list of “contract bullets” from the Bash phase (or the Bash diff).
- *Prompt shape*:
  - “Turn these contract bullets into a formal subsection for ZEPHYR_SYSTEM_DESIGN.md: [paste bullets]. Use the same heading level and table format as the existing ‘Launcher options’ section. Do not invent any new options or paths; only what is in the bullets.”
  - “We have a new entrypoint =my-entrypoint.sh=. Add a row to the entrypoint table: name, path in container, purpose, args, env vars read.”
- *Done*: Contract subsection is in the doc; no invented names (all from bullets or existing contract).

*** Area 3 — Rust porting (Kimi)

- *Context to attach*: Contract subsection; Bash code; =crates/zephyr/src/paths.rs=, =config.rs=, and the relevant =host/*.rs= or =container/*.rs=.
- *Prompt shape*:
  - “Port the [feature] from Bash to Rust. Contract: [paste]. Use only types and constants from =paths.rs= and =config.rs=; do not hardcode paths or env names. Add tests that assert the contract (paths, env vars).”
  - “Implement the same behavior as =launch_container.sh= for [X]. In Rust use =HostLayout= for paths and =ZephyrConfig= for options. See =host/docker_args.rs= for how we add env vars.”
- *Chunking*: One feature per turn is fine if contract is clear. Say explicitly: “use only paths from paths.rs”.
- *Done*: Rust implements the contract; no hardcoded paths; tests reference contract or =paths.rs=.

*** Area 4 — Testing (Kimi)

- *Context to attach*: Contract; =paths.rs= / =HostLayout=; the Rust module and its tests.
- *Prompt shape*:
  - “Add tests for [feature]. Assert: (1) path used is from =HostLayout= (or =container_paths=); (2) env var name matches contract; (3) exit code or argv shape matches contract.”
- *Done*: Tests pass and reference contract or repo path constants.

*** Area 5 — Debugging (Kimi)

- *Context to attach*: Contract; Bash and Rust code; the mismatch.
- *Prompt shape*:
  - “Bash uses path P1, Rust uses P2. Contract says [X]. Which of P1 or P2 is correct? Fix the wrong one and ensure the fix uses =paths.rs= or the contract, not a new literal.”
- *Done*: One side fixed; both use contract or =paths.rs=.

*** Kimi — Pitfalls and mitigations

| Pitfall | Mitigation |
|---------+------------|
| Invents =/opt/foo= or =MY_VAR= | “Use only paths from =paths.rs= and env names from the contract or =config.rs=.” |
| Assumes “standard” layout | Attach =HostLayout= or the layout section of the contract. |
| Chinese comments in codebase | Kimi can align; if you want English-only, say “keep all new comments in English.” |

** GLM (Zhipu / ChatGLM)

*** Profile
- *Strength*: General code generation; Chinese context; can follow stepwise instructions.
- *Weakness*: May skip steps if the prompt has many; sometimes invents APIs; needs explicit “only use repo types”.

*** Area 1 — Bash prototyping (GLM)

- *Context to attach*: The single file to edit; the exact function or line range (e.g. “=main()= in launch_container.sh, lines 518–545”).
- *Prompt shape* (stepwise):
  - “Step 1: In =container/launch_container.sh=, in the =main()= argument loop, add a case for =--run-id= that sets =run_id= to the next argument. Step 2: After the loop, if =run_id= is empty, set =run_id= to =run-$(date +%Y%m%d-%H%M%S)-$$=. Do only Step 1 in this response.”
  - (Next message) “Step 2: [as above]. Then Step 3: In =build_docker_args=, add =SYGALDRY_RUN_ID= to the env list with value =${_cfg[run_id]}=. Do Step 2 and 3.”
- *Chunking*: Prefer one or two steps per message. If the model skips a step, send a follow-up: “You did Step 1; now do Step 2 only.”
- *Done*: Each step confirmed; script runs and shows the new behavior.

*** Area 2 — Contract writing (GLM)

- *Context to attach*: The contract file and the exact place to add (e.g. “after the ‘Launcher options’ table”); the Bash change in one paragraph.
- *Prompt shape*:
  - “Step 1: Add one row to the Launcher options table: =--run-id=, env =SYGALDRY_RUN_ID=, default =run-<date>-<pid>=. Step 2: Add one sentence: ‘Used for tracing and lease identity.’ Do both steps.”
- *Done*: One table row or one short paragraph; no long prose.

*** Area 3 — Rust porting (GLM)

- *Context to attach*: The Bash block (10–20 lines) and the Rust file + module (e.g. =config.rs=, =ZephyrConfig= and =CliOverrides=).
- *Prompt shape*:
  - “Port this Bash logic to Rust. Bash: [paste]. In =config.rs= add =run_id= to =CliOverrides= and resolve it in =ZephyrConfig::from_env= using the same default format as Bash. Use only types already in =config.rs=; do not create new modules.”
  - (Next) “In =host/docker_args.rs=, add =SYGALDRY_RUN_ID= to the env list when =config.run_id= is set. Use the same env var name as in the contract. Do not add any other env vars.”
- *Chunking*: One module per message. After each response: “Confirm: did you use only types from =config.rs= and =error.rs=? List any new type you added.”
- *Done*: Rust builds; no new external types; behavior matches the Bash block.

*** Area 4 — Testing (GLM)

- *Context to attach*: The test file (e.g. =cli.rs= tests or =host/docker_args.rs= tests) and the contract sentence for the feature.
- *Prompt shape*:
  - “Add one test: =test_run_id_in_cli=. Parse args =[\"zephyr\", \"--run-id\", \"myrun\", \"shell\"]= and assert =cli.run_id == Some(\"myrun\")=. Put it in the existing =#[cfg(test)]= block in =cli.rs=.”
- *Done*: One test added; =cargo test test_run_id_in_cli= passes.

*** Area 5 — Debugging (GLM)

- *Context to attach*: One file and one wrong line or one wrong value.
- *Prompt shape*:
  - “In =host/docker_args.rs= we pass =RUN_ID= to the container. The contract says the env var must be =SYGALDRY_RUN_ID=. Change =RUN_ID= to =SYGALDRY_RUN_ID= in that file.”
- *Done*: Single fix applied; re-run tests.

*** GLM — Pitfalls and mitigations

| Pitfall | Mitigation |
|---------+------------|
| Skips Step 2 or 3 | Send “Do only Step 2” in a follow-up; or one step per message. |
| Invents =std::zephyr::config= or similar | “Use only types and functions from =crates/zephyr/src/=; list the files you are allowed to use.” |
| Adds extra logic | “Implement only what the Bash block does. Do not add error handling or options not in the contract.” |

** Generic / unknown model

*** Universal rules
- Apply the ideal workflow strictly: Bash first → contract → Rust.
- Prefer smaller, atomic prompts. Always attach or link the contract when asking for Rust.
- After any Rust change, ask: “Does this match the contract? List any behavior that differs from the Bash version.”

*** Area 1–5 (generic)
- *Context*: Always include the contract (or the relevant subsection) and the file(s) being edited.
- *Prompt*: Be explicit: “Implement X. Contract says [paste]. Do not add behavior beyond the contract.”
- *Done*: Feature works in Bash; contract written; Rust matches contract; tests added where feasible.

* Checklist for agents (any model)

** Before adding Rust for a feature
- [ ] The behavior exists and works in Bash (or the current script surface).
- [ ] The contract is written (options, paths, env, exit codes, file formats).
- [ ] The contract is in =ZEPHYR_SYSTEM_DESIGN.md= or =CONTRACT.md= (or equivalent).

** When writing Rust
- [ ] Only implement what the contract specifies.
- [ ] Add tests that assert contract (e.g. same argv, same exit code, same paths).
- [ ] Use repo error and config patterns (=error.rs=, =config.rs=, =paths.rs=).

** After Rust port
- [ ] CI or a manual check compares Bash vs Rust for the same scenario where feasible.
- [ ] Docs (CLAUDE.md, AGENTS.md, or this file) mention that this feature is “formalized in Rust” and point to the contract.
