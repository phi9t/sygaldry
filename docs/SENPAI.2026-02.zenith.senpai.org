* 1. Executive Summary
** 1.1 Problem Statement
Zephyr images are very large (spack ~63GB, mlsys ~71GB) and current publishing relies on direct ~docker push~ from local daemon flows. We have observed push instability at manifest finalization for large tags, causing release inconsistency risk.

** 1.2 Engineering Impact
- Slower and less reliable release operations for NCCL-enabled torch snapshots.
- Risk of moving tags diverging from validated candidate/date tags.
- Increased operational overhead for recovery and rollback.

** 1.3 Decision Snapshot
- Keep runtime contract unchanged for existing Zephyr tags.
- Keep GHCR-only publishing.
- Implement digest-first candidate -> verify -> promote workflow.
- Implement pipeline first (no immediate stable tag cutover in Wave 1).
- Add optional containerd-first acceleration lane as future work.

* 3. Upstream & Tooling Research
** 3.1 Spack containerize model
Spack ~containerize~ generates multi-stage Dockerfiles and favors small runtime stages with ~spack gc -y~ and optional binary stripping.

** 3.2 Spack OCI buildcache model
Spack ~buildcache push --base-image --tag~ pushes OCI-native package layers and composes runnable tags from root specs and runtime deps. This improves dedup and can serve as buildcache + runtime artifact model.

** 3.3 Skopeo
~skopeo copy/sync~ is daemonless, supports retries and digest preservation, and is suitable for robust promotion/copy operations between registry references.

** 3.4 Crane
~crane copy/tag/digest/index~ supports efficient remote manifest/tag operations without daemon coupling and is a strong fit for digest-driven promotion.

** 3.5 Nydus
Nydus provides conversion and chunk-level dedup/lazy pull improvements but requires containerd snapshotter ecosystem for primary benefits. It is suitable as an optional containerd-first lane, not immediate default for Docker runtime parity.

** 3.6 Comparative Fit for Wave 1
- Primary release reliability: BuildKit + digest manifest + crane/skopeo promotion.
- Immediate runtime compatibility: preserve current OCI image contract.
- Future acceleration lane: nydus tags for containerd deployments.

* 4. Proposed Architecture
** 4.1 Goals
- Deterministic, recoverable release flow.
- No runtime contract break.
- Reliable large-artifact publishing.
- Enforced release gates for NCCL/JAX/CUDA parity.

** 4.2 Non-Goals (Wave 1)
- No immediate migration to full Spack OCI buildcache as primary runtime path.
- No mandatory nydus deployment.
- No moving-tag production cutover during initial implementation phase.

** 4.3 Reference Flow
1. Build candidate images (~<name>-<date>-<sha>~).
2. Verify candidate image set.
3. Emit immutable release manifest (digest map).
4. Promote moving tags by digest (dry-run first in Wave 1).
5. Rollback by previously emitted manifest.

** 4.4 Artifact Model
Release manifest (~image-set.json~):
- schema version
- release metadata
- image rows (~name~, ~candidate_tag~, ~stable_tag~, ~source_ref~, ~source_digest~)

** 4.5 Trust and Reproducibility
- Promotion always references immutable digest.
- Candidate validation precedes promote.
- Rollback references prior manifest exactly.

* 5. Interface & Contract Specification
** 5.1 New CLI
~container/publish.sh~ subcommands:
- ~build-candidates~
- ~verify-candidates~
- ~promote~
- ~rollback~

** 5.2 New manifest outputs
- ~container/releases/<release_id>/image-set.json~

** 5.3 Promotion semantics
- Prefer remote retag/copy via ~crane~.
- Fallback via ~skopeo copy --preserve-digests~.
- Always support ~--dry-run~.

* 6. Detailed Workflow Specs
** 6.1 Candidate Build Workflow
- Build/push candidate tags only (CI).
- Record digest for each candidate tag.

** 6.2 Verify Workflow
- Ensure manifests exist for all candidates.
- Optional strict mode can include runtime checks if runner has GPU.

** 6.3 Promote Workflow
- Input: ~image-set.json~.
- For each image, retag digest-backed candidate to moving tag.
- Fail if any candidate digest is unresolved.

** 6.4 Rollback Workflow
- Input: prior ~image-set.json~.
- Re-apply moving tags to previous digests.

* 7. Size Optimization Plan
** 7.1 Snapshot Dockerfile layering
Current flow copies ~._view~ then deletes/regenerates it later. Wave 1 refactors to avoid that copy-delete pattern:
- copy install_tree + metadata only
- create empty ~._view~ directory
- regenerate view once

** 7.2 Budget Gates
Add wave-2 guardrails for layer-count and compressed-size regression thresholds.

* 10. Risks and Mitigations
** 10.1 Registry finalization hangs
Mitigation: decouple build and promote; use digest-first promotion with tool fallbacks.

** 10.2 Tag drift
Mitigation: treat ~image-set.json~ as source of truth and require it for promotion.

** 10.3 Contract regression
Mitigation: keep runtime contract unchanged; enforce existing verification scripts.
