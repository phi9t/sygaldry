● Temporal System Design Review

  The system is a Go-based DAG pipeline orchestrator built on Temporal, spanning
   ~3,500 lines across 17 files. Here's the assessment:

  ---
  Architecture Overview

  YAML Plan → orchestrate CLI (validate) → Temporal Pipeline Workflow → Worker
  (8 activities) → events.jsonl + logs

                       ↓

        logs_cli.py / web visualizer

  Two workflow modes:
  - Pipeline (internal/workflows/pipeline.go) — DAG execution with dependency
  resolution, parallel batches, conditional skip logic, allow_failure
  - Orchestration (internal/workflows/orchestration.go) — Legacy sequential
  mode, kept for backward compat

  8 activity types in internal/activities/steps.go (795 lines): command,
  download, docker_build, docker_push, package_build, container_job,
  hf_download_dataset, hf_download_model

  ---
  Strengths

  1. Three-stream structured logging — Each activity writes stdout.log,
  stderr.log, and structured.jsonl (JSONL with timestamps, stream markers,
  partial-line detection). Excellent for both human tailing and agent parsing.
  2. Solid pre-flight validation (cmd/orchestrate/main.go:97-174) — Validates
  step IDs, types, required fields per type, dependency references, and when
  clause references before submitting to Temporal.
  3. 89 test cases across activities, pipeline logic, and plan validation. Good
  coverage of happy paths and edge cases.
  4. DAG scheduling — Batch-parallel execution of all ready steps per iteration,
   with deadlock/stall detection. When clauses enable conditional branching (run
   step only if another succeeded/failed).
  5. Log truncation — Stdout/stderr truncated to TEMPORAL_LOG_MAX_BYTES (10KB
  default) in Temporal payloads, full logs preserved on disk. Prevents payload
  bloat on long-running jobs.

  ---
  Issues Found

  High priority:

  1. No cycle detection in DAG (pipeline.go:147) — The scheduler loop assumes an
   acyclic graph. Circular depends_on references would cause a deadlock error at
   runtime rather than a clear validation error upfront. The validatePlan
  function checks that deps exist but never checks for cycles.
  2. Environment variable append semantics (steps.go:660-665) — Env vars are
  appended to os.Environ() rather than overriding. If the parent process has
  FOO=bar, a step setting FOO=baz won't override it — the OS will see both, and
  behavior depends on which one the runtime picks first (typically the first).
  Should use explicit override logic.

  Medium priority:

  3. Retry policy is global (pipeline.go:138-145) — All activities get the same
  retry: 3 attempts, 5s initial, 2x backoff, 1min max. There's no per-step
  override. A quick command step and a 24-hour container_job get identical retry
   behavior.
  4. Silent YAML field ignoring — yaml.Unmarshal silently drops unknown fields.
  A typo like comand instead of command would pass validation as an empty
  command step. Could use KnownFields(true) on the decoder.
  5. Log directory fallback to /tmp (steps.go:183-184) — If the primary log
  directory fails to create, falls back to /tmp/temporal-logs. This is
  non-persistent and would lose logs across reboots with no warning.
  6. HF dataset default split (steps.go:571-576) — Default split is train[:100]
  (only 100 samples). Easy to miss and would silently produce incomplete
  downloads.

  Low priority:

  7. No worker tests — cmd/worker/main.go has zero test coverage.
  8. Visualizer has no auth — Anyone on the network can view all runs/logs at
  port 8787.
  9. No log retention — Logs accumulate indefinitely with no cleanup mechanism.

  ---
  Design Observations

  Pipeline scheduling algorithm (pipeline.go:147-239):
  while pending steps remain:
      collect runnable (deps complete + not skipped)
      skip steps with unmet `when` conditions or failed deps
      if no progress + no runnable → deadlock error
      execute all runnable in parallel batch
      wait for batch to complete
      on failure: stop pipeline (unless allow_failure)

  This is correct for a single-worker model but has a subtle behavior: all steps
   in a batch start simultaneously but the workflow waits for all to finish
  before scheduling the next batch. A slow step in batch N blocks everything in
  batch N+1 even if some batch-N+1 steps only depended on fast batch-N steps.
  True streaming DAG execution (schedule-on-complete rather than
  batch-on-complete) would improve throughput.

  Structured log format is well-designed:
  {"timestamp":"...","workflowId":"...","stepId":"...","stream":"stdout","messag
  e":"...","partial":false}
  The partial flag handles progress bars and incomplete lines correctly.
  Carriage returns are stripped for clean output.

  ---
  Summary

  The Temporal system is well-architected for its scope — clean separation
  between validation, scheduling, execution, and observability. The 8 activity
  types cover the Sygaldry use cases well (container jobs, HF downloads, Docker
  builds). Test coverage is strong at 89 cases.

  The main gaps are cycle detection and env var override semantics (both fixable
   in <50 lines each), and the longer-term improvements would be per-step retry
  policies and streaming DAG scheduling instead of batch scheduling. Want me to
  implement any of these fixes?
