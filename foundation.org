This document is the authoritative engineering design for the Zephyr container
infrastructure.  It describes every core subsystem at implementation depth:
data structures, control flow, error handling, file formats, and operational
procedures.  New features MUST be designed in accordance with these principles;
deviations require explicit justification and an update to this document.

This document is human-reviewed and updated by both agents and humans; it is
the source of truth for future design.

The six foundational pillars, in dependency order:

1. *Spack Foundation Build Layer* -- immutable core packages (PyTorch, JAX, LLVM, Triton).
2. *Container Entrypoint Architecture* -- dual-persona execution for humans and agents.
3. *Snapshot and Registry Pipeline* -- bake validated environments into portable images.
4. *Spack Staging Mechanism* -- safely develop new foundation layers without disturbing production.
5. *Spack+UV Package Synergy* -- strict ownership boundary between Spack core and UV application packages.
6. *MLSys Application Images* -- HF, vLLM, sglang, TorchTitan, Megatron-LM, and beyond.

#+begin_quote
"Build heavy dependencies once with Spack; bake the validated environment into
snapshot images; layer application packages with UV on top of Spack without
ownership conflicts."
#+end_quote

Sygaldry combines Docker (isolation), Spack (HPC/scientific deps), Bazel
(incremental builds), and uv (Python).  Key benefits: hermetic builds,
reproducibility, multi-layer caching, dynamic UID/GID mapping.  High-level
overview: =SYSTEM_DESIGN.md=; infra contract: =container/ZEPHYR_SYSTEM_DESIGN.md=.

** Layers

1. *Container* (Docker) — OS isolation, reproducible runtime, GPU access.
2. *Dependency* (Spack) — external scientific/HPC libraries, unified view at =/opt/spack_store/view=.
3. *Build* (Bazel) — fast incremental builds, sandboxing, multi-language.
4. *Python* (uv) — application packages on top of Spack, shared cache.

** Dependency pinning

- *System*: Docker base image tags (e.g. =nvidia/cuda:12.9.1-cudnn-devel-ubuntu24.04=).
- *External*: =spack.lock= for exact Spack versions.
- *Application*: Bazel =WORKSPACE=, uv lockfiles.

** Data flow

Source (host) → Container → Spack view (=/opt/spack_store/view=) → Bazel/uv →
application artifacts → host output directory.

** Cache hierarchy

Docker layer cache → Spack binary cache → Bazel cache → uv cache.  Layout and
mounts: see *Host Storage Layout*.

* Pillar 1: Spack Foundation Build Layer
:PROPERTIES:
:CUSTOM_ID: spack-foundation
:END:

** Problem Statement

Machine learning workloads depend on a deep stack of CUDA-compiled native
libraries (PyTorch, JAX, Triton, LLVM, cuDNN, NCCL) whose compilation takes
3-8 hours and produces ~42 GB of artifacts.  These libraries have intricate ABI
coupling: a PyTorch built against CUDA 12.9 and cuDNN 9.10 must use exactly
those runtime versions, and JAX must share the same CUDA/cuDNN stack.  Pip
cannot manage this correctly because it treats each package as independent.

Spack solves this with unified concretization: a constraint solver that
guarantees every package in the environment uses exactly one version of every
shared dependency.

** Architecture

*** Layered Dependency Model

Docker Base Layer (=nvidia/cuda:12.9.1-cudnn-devel-ubuntu24.04=)
  CUDA 12.9.1 toolkit, cuDNN 9.10.2, NCCL
  Declared as Spack externals: these are shipped in the base image and are NOT built by Spack.

Spack Build Layer (=pkg/zephyr/spack_src.yaml=)
  py-torch 2.9 +cuda +distributed -magma
  py-jaxlib 0.7 +cuda
  py-triton 3.4
  llvm 20 +clang +lldb
  py-numpy, py-scipy
  python 3.13

*** Spack View

The Spack view at =/opt/spack_store/view= is a symlink tree that merges all
installed packages into a single prefix.  Downstream consumers (UV, entrypoints,
Bazel, application code) reference this path only -- never the install tree
hashes directly.

**** View options (spack.yaml)

- *path* (required) :: View root.  We use =/opt/spack_store/view= (simple form in =pkg/zephyr/spack_src.yaml=: =view: /opt/spack_store/view=).
- *link* :: =link= (default, symlinks) | =copy= | =hardlink=.  Symlink avoids duplication; copy/hardlink skip externals.  We use the default.
- *projection* :: Optional pattern (e.g. ={name}= or ={name}-{version}=) for layout under the view; default merges all packages into a single =bin/=, =lib/=, =lib/pythonX.Y/site-packages=, etc.
- *Unification* :: =concretizer: unify: true= ensures one concrete spec per package so the view can merge all install trees without path conflicts (see P1.1).
- *Regeneration* :: View is updated by =spack install= or explicitly via =spack env view regenerate=.

**** Container leverage of the view path

The container infrastructure uses =/opt/spack_store/view= as the single
integration point in these ways:

- *Single integration point* :: One prefix for =PATH= (=view/bin=), =PYTHONPATH= / =LD_LIBRARY_PATH= (=view/lib=, =view/lib/pythonX.Y/site-packages=).  Tools and runtimes need no per-package paths.
- *Fallback when activation fails* :: =container/entrypoints/default.sh= (=ensure_spack_view_fallback=), =run-job.sh=, =verify-gpu.sh= inject =view/bin=, view site-packages, and =view/lib= / =view/lib64= when =spack env activate= is unavailable (e.g. no repo, baked image only).
- *uv integration* :: =container/entrypoints/uv-install.sh= uses =SPACK_PY=/opt/spack_store/view/bin/python3=, creates venvs with =--system-site-packages= and a =spack-view.pth= pointing at the view's site-packages; =container/setup_user_environment.sh= =configure_uv_spack()= sets =PYTHONPATH= and =UV_FIND_LINKS= from the view when present.
- *Verification* :: =container/verify_uv_spack.py= and =verify-spack.sh= require core packages to resolve from the view; T8.2/T8.4 enforce "from view" and "no nvidia-* outside view."
- *Snapshot baking* :: View lives under =._view/<hash>/= on the host; =container/spack_snapshot.dockerfile= copies =._view= and creates =/opt/spack_store/view= → =._view/<hash>/=; =container/snapshot_spack.sh= checks =._view= exists before snapshot.

*** External CUDA Binding

CUDA and cuDNN are declared as non-buildable externals in =spack_src.yaml=:

#+begin_src yaml
packages:
  cuda:
    externals:
      - spec: cuda@12.9.1
        prefix: /usr/local/cuda
    buildable: false
  cudnn:
    externals:
      - spec: cudnn@9.10.2
        prefix: /usr/local/cuda
    buildable: false
#+end_src

This means Spack links against the Docker base image's CUDA but never compiles
it.  The Dockerfile ensures cuDNN headers and libraries are copied to
=/usr/local/cuda/include= and =/usr/local/cuda/lib64= so Spack's external
discovery finds them.

*** Concretizer Configuration

#+begin_src yaml
spack:
  concretizer:
    unify: true    # Single version per dependency across entire env
    reuse: false   # Do not reuse host microarch builds
  packages:
    all:
      require:
        - "target=x86_64"  # Generic target, no microarch tuning
#+end_src

- =unify: true= is critical.  Without it, PyTorch and JAX could each pull in
  different numpy/scipy versions, causing import conflicts.
- =reuse: false= prevents accidentally reusing a package compiled for
  skylake/haswell on a different microarchitecture.
- =target=x86_64= makes the entire store portable across any x86_64 machine.

** Build Script Control Flow

=pkg/zephyr/build.sh= implements the build with two distinct paths:

*** Lockfile Path (deterministic installs)

#+begin_example
spack.lock exists?
  ├── YES → Parse lock roots → Install each root by hash (/{hash})
  │         ├── Non-librosa roots: install unconditionally
  │         └── Librosa roots: guarded install with dry-run check
  │             ├── Dry-run touches torch/jax → skip librosa
  │             └── Dry-run clean → attempt install (non-fatal on failure)
  └── NO  → Concretize from spack_src.yaml → Dry-run safety check → Install
#+end_example

*** Forbidden Rebuild Guard

The guard is implemented as a regex match on Spack's install output:

#+begin_example
FORBIDDEN_REBUILD_PATTERN='(^|[^[:alnum:]_-])(py-torch|py-jax|py-jaxlib|torch|jax|jaxlib)([^[:alnum:]_-]|$)'
#+end_example

The =contains_forbidden_rebuilds()= function pipes any Spack dry-run output
through =rg= with this pattern.  If it matches, the build aborts immediately.
This guard runs in two places:

1. Before fresh concretization installs (no lockfile path).
2. Before librosa root installs (lockfile path, guarded policy).

*** Librosa Policy

Librosa is a heavyweight audio library whose transitive dependencies sometimes
conflict with the core torch/jax stack.  The build script implements a
three-mode policy controlled by =SYGALDRY_LIBROSA_POLICY=:

| Policy    | Behavior                                                         |
|-----------+------------------------------------------------------------------|
| =guarded= | Default.  Dry-run first; skip if torch/jax would be rebuilt.     |
| =remove=  | Never install librosa.                                           |
| =keep=    | Install without dry-run guard (may fail; non-fatal).             |

** Design Principles

*** P1.1: Unified Concretization

All packages use =unify: true=.  This is non-negotiable.  Without it, Spack may
resolve py-torch against numpy 1.x while py-jax resolves against numpy 2.x,
producing silent import errors or segfaults.

*** P1.2: External CUDA Provider

CUDA and cuDNN are external.  Spack never builds them.  This saves hours of
compilation and guarantees the container's CUDA runtime matches the driver.

*** P1.3: Broad GPU Architecture Support

A single build covers Pascal through Hopper (6 architectures).  This trades
~20% larger fatbinary size for zero need to maintain per-GPU builds.

*** P1.4: Generic x86_64 Target

No host microarchitecture tuning (=target=x86_64=).  A Spack store built on an
AMD EPYC server works on an Intel Xeon workstation without recompilation.

*** P1.5: Lockfile Discipline

When =spack.lock= exists, the build script installs by hash (=/{hash}=) without
re-concretizing.  This guarantees bit-for-bit reproducibility.  The lockfile
is a precious artifact checked into the repository.

*** P1.6: Forbidden Rebuild Guard

If the resolver attempts to rebuild torch/jax/jaxlib, the build fails immediately.
These packages take 2-6 hours each.  The guard prevents operator error (e.g.,
bumping a spec that triggers a transitive rebuild of torch).

*** P1.7: View as Integration Surface

The Spack view at =/opt/spack_store/view= is the sole integration point for
downstream consumers.  UV, entrypoints, and application code all reference
the view -- never the install tree hashes directly.  See *** Spack View for
view options and container leverage.

** Operational Procedures

*** Building the Foundation Layer from Scratch

#+begin_example
# 1. Launch builder container with host Spack store mounted
SYGALDRY_BUILD_ROLE=builder ./container/launch_container.sh --entrypoint spack-build

# Build script handles:
#   - spack_src.yaml → spack.yaml
#   - spack concretize --force
#   - forbidden rebuild guard
#   - spack install
#   - spack env view regenerate
#   - Emits spack.lock for future deterministic builds
#+end_example

*** Adding a New Package to the Foundation

#+begin_example
# 1. Edit pkg/zephyr/spack_src.yaml: add the new spec
# 2. Use staging (Pillar 4) to evaluate safety
# 3. If staging passes: rebuild with updated spack_src.yaml
# 4. Commit updated spack.yaml + spack.lock
# 5. Rebuild snapshot (Pillar 3)
#+end_example

*** Upgrading a Core Package (e.g., PyTorch 2.9 → 2.10)

This is the most dangerous operation.  PyTorch upgrades can cascade rebuilds
across the entire dependency tree.

#+begin_example
# 1. Edit spack_src.yaml: bump py-torch version
# 2. Delete spack.lock (force fresh concretization)
# 3. Run staging: tools/zephyr_stage_spack.sh
#    - Staging will fail at forbidden guard if torch must rebuild (expected)
#    - Review concretize_report.json for the full rebuild set
# 4. If acceptable: run full build with builder role
# 5. Full GPU verification: verify-spack.sh, verify-gpu.sh
# 6. Commit new spack.lock + rebuild snapshot
#+end_example

* Pillar 2: Container Entrypoint Architecture
:PROPERTIES:
:CUSTOM_ID: entrypoints

** Problem Statement

The container must serve two radically different user personas:

1. *Human developers* need a rich interactive experience: welcome banners, GPU
   status, convenience aliases, environment auto-activation, and an intuitive
   bash shell.
2. *Coding agents and CI jobs* need a headless execution path: deterministic
   exit codes, no interactive prompts, minimal stdout noise, and structured
   logging for machine consumption.

Both personas must share the same Spack+CUDA initialization to avoid behavioral
divergence.

** Architecture

*** Entrypoint Lifecycle

Every container run goes through this lifecycle:

#+begin_example
┌─────────────────────────────────────────────────────────────────────────┐
│ Docker ENTRYPOINT: /opt/container_entrypoints/<name>.sh                │
│                                                                        │
│ Phase 1: Spack Initialization (shared across all entrypoints)          │
│   source /opt/spack_src/share/spack/setup-env.sh                       │
│                                                                        │
│ Phase 2: Spack Environment Activation (cascade)                        │
│   SYGALDRY_SPACK_ENV → /opt/spack_env/default → workspace/pkg/zephyr  │
│   Fallback: direct /opt/spack_store/view PATH/PYTHONPATH injection     │
│                                                                        │
│ Phase 3: CUDA Environment Setup                                        │
│   CUDA_HOME=/usr/local/cuda, PATH, LD_LIBRARY_PATH                     │
│                                                                        │
│ Phase 4: MLSys Venv Auto-Activation (if SYGALDRY_MLSYS_ENV set)       │
│   Single venv: source /opt/mlsys-envs/<env>/bin/activate               │
│   Multi-venv: find first sub-venv or use SYGALDRY_MLSYS_TARGET         │
│                                                                        │
│ Phase 5: Persona-Specific Dispatch                                     │
│   default.sh  → GPU validation → welcome banner → exec bash -i         │
│   run-job.sh  → exec "$@"                                              │
│   verify-*.sh → run checks → exit 0/1                                  │
│   uv-install  → build venv → exit 0/1                                  │
│   spack-*.sh  → builder role check → build → exit 0/1                  │
│   hf-download  → download → exit 0/1                                   │
└─────────────────────────────────────────────────────────────────────────┘
#+end_example

*** Spack Environment Activation Cascade

The cascade is the same in every entrypoint and tries locations in priority
order:

#+begin_example
1. $SYGALDRY_SPACK_ENV           (explicit override, e.g., staging env)
2. /opt/spack_env/default        (baked into snapshot image)
3. /opt/spack_env/zephyr         (legacy baked name)
4. $SYGALDRY_ROOT/pkg/zephyr     (workspace-mounted, legacy mode)
5. [FALLBACK] /opt/spack_store/view → inject into PATH/PYTHONPATH/LD_LIBRARY_PATH
#+end_example

The fallback (step 5) exists because in some edge cases (fresh image, missing
spack.lock) the formal Spack activation fails.  The view fallback ensures
torch/jax remain importable.

** Entrypoint Detailed Design

*** =default.sh= -- Human Interactive Shell

Control flow:

1. Spack init + cascade activation
2. View fallback if torch/jax not importable
3. *GPU fail-fast validation*: runs Python script that checks:
   - =torch.cuda.is_available()= and =torch.cuda.device_count() >= 1=
   - =jax.devices()= contains at least one GPU device
   - If either fails → print error to stderr → =exit 1=
4. MLSys venv auto-activation (=_activate_baked_mlsys_venv=)
5. Set convenience aliases:
   - =gpu-test= → quick PyTorch CUDA check
   - =jax-test= → quick JAX GPU check
   - =spack-build= → cd to env + run build.sh
   - =hf-dataset()= → quick dataset download function
6. If =$#= > 0: =exec "$@"= (non-interactive)
7. Otherwise: print welcome banner → =exec bash -i=

The welcome banner adapts to the image type:
- Base/snapshot: shows Spack commands, paths.
- MLSys image: shows env name, active venv, =mlsys-activate= hint.

*** =run-job.sh= -- Agent Headless Execution

Control flow:

1. =set -euo pipefail= (strict error handling)
2. Spack init + cascade activation
3. View fallback (no GPU validation -- job may be CPU-only setup)
4. MLSys venv auto-activation
5. =exec "$@"= -- replace the shell with the command

Key differences from =default.sh=:
- No GPU fail-fast (some jobs are setup steps that don't need GPU)
- No welcome banner
- No aliases
- The exit code of the user's command becomes the container's exit code

*** =spack-build.sh= / =spack-install.sh= -- Builder Role Entrypoints

#+begin_example
if SYGALDRY_BUILD_ROLE != "builder":
    echo "ERROR: Spack builds are restricted to the builder role." → exit 1
#+end_example

These entrypoints refuse to run unless the builder role is explicitly set.  This
prevents consumer containers from accidentally mutating the Spack store.

=spack-build.sh= resolves the build environment using the same cascade
(=SYGALDRY_SPACK_ENV= → =/opt/spack_env/default= → workspace) and then invokes
=./build.sh= in that directory.

*** =uv-install.sh= -- UV Venv Builder

Detailed in Pillar 5.  Core logic:

1. Find Spack Python (=/opt/spack_store/view/bin/python3=)
2. Read =spack_owned_packages.conf= → set =UV_NO_BUILD_ISOLATION_PACKAGE=
3. Locate =nvidia_overrides.txt=
4. =uv venv --python <spack-py> --system-site-packages $VENV_DIR=
5. Write =.pth= file for Spack view site-packages
6. Generate constraint file from Spack-owned package versions
7. =uv pip install --constraint <constraints> --override <nvidia-overrides> "$@"=

*** =verify-gpu.sh= -- GPU Hardware Validation

Reports:
- NVIDIA driver version, GPU name, memory (via =nvidia-smi=)
- CUDA toolkit version (via =nvcc=)
- =torch.cuda.is_available()=, device name, CUDA version, cuDNN version
- =jax.devices()= and GPU device count

Exit code 0 if both frameworks see GPU, non-zero otherwise.

*** =verify-spack.sh= -- Spack Environment Integrity

Four-step verification:

| Step | What it does                                                       |
|------+--------------------------------------------------------------------|
| 1    | Check =/opt/spack_store/view/bin= exists, torch/jax importable    |
| 2    | Import torch, check CUDA available, report device/version          |
| 3    | GPU tensor matmul: 100x100 matrix multiply on CUDA                |
| 4    | Neural network: 3-layer MLP forward + backward pass on GPU        |

The NN test exercises:
- =torch.nn.Linear=, =torch.nn.ReLU= on CUDA
- Forward pass with 32-sample batch
- =loss.backward()= to verify gradient computation
- Gradient existence check for all named parameters

JAX verification mirrors this:
- Matrix multiply on GPU
- 2-layer MLP with =jax.grad()= for gradient computation
- Shape assertions on all gradient tensors

*** =hf-download.sh= -- HuggingFace Asset Download

Modes:
- =dataset <id> [config] [split]= → =datasets.load_dataset()=
- =model <model_id>= → =huggingface_hub.snapshot_download()=

Creates a lightweight UV venv at =/opt/uv_cache/venvs/hf-download= with just
=datasets= and =huggingface-hub= (not the full Spack stack).  Downloads go to
=HF_HOME= (default =/opt/hf_cache=, shared across projects).

** Baked Entrypoints

All entrypoints are COPYd into the image at =/opt/container_entrypoints/=:

#+begin_example
# In dev_container.dockerfile:
COPY --chown=kvothe:kvothe container/entrypoints /opt/container_entrypoints
RUN chmod +x /opt/container_entrypoints/*.sh

# Image label signals baked status:
LABEL sygaldry.entrypoints.baked="true"
#+end_example

The launcher checks this label via =docker inspect= and resolves entrypoint
paths accordingly.  This means the container is fully self-contained --
no host-mounted scripts are needed.

** Design Principles

*** P2.1: Shared Initialization, Divergent Dispatch

All entrypoints share phases 1-4 (Spack, CUDA, MLSys venv).  They diverge only
at phase 5 (dispatch).  This prevents behavioral drift between interactive
and headless modes.

*** P2.2: GPU Fail-Fast (Interactive Only)

Only =default.sh= gates on GPU availability.  =run-job.sh= does not because
some agent jobs (file processing, dataset preparation) may legitimately run
without GPU.  The GPU check is a 3-second Python script, not a heavy operation.

*** P2.3: =exec= Semantics

All entrypoints use =exec= for the final command dispatch.  This replaces
the shell process with the target process, ensuring:
- Correct signal propagation (SIGTERM reaches the user's process)
- The container exit code equals the command's exit code
- No zombie shell process

*** P2.4: Builder Role is a Hard Gate

The builder role check (=SYGALDRY_BUILD_ROLE=builder=) is the first thing
=spack-build.sh= does.  If missing, it exits immediately.  This prevents
any consumer workflow from accidentally running =spack install=.

* Pillar 3: Snapshot and Registry Pipeline
:PROPERTIES:
:CUSTOM_ID: snapshot
:END:

** Problem Statement

The Spack store is 42 GB and takes hours to build.  It must be shared across
machines, CI runners, and developer workstations without requiring each to
run the build.  Docker images are the natural distribution mechanism, but
naively COPYing 42 GB into an image requires careful selection of what to
include and robust verification.

** Three-Stage Image Architecture

#+begin_example
Stage 1: Base Image (sygaldry/zephyr:base)                    ~15 GB
  FROM nvidia/cuda:12.9.1-cudnn-devel-ubuntu24.04
  ├── System packages: build-essential, cmake, ninja, git, etc.
  ├── Language runtimes: Python 3.13, Go 1.21.5, Bazel 6.4.0
  ├── Spack source: /opt/spack_src (v1.1.0, ~150 MB)
  ├── UV package manager: /usr/local/bin/uv
  ├── Baked env metadata: /opt/spack_env/default/spack_src.yaml
  ├── Baked entrypoints: /opt/container_entrypoints/*.sh
  ├── Override files: spack_owned_packages.conf, nvidia_overrides.txt
  └── User kvothe: dynamic UID/GID from build args

Stage 2: Spack Snapshot (sygaldry/zephyr:spack)               ~37 GB
  FROM sygaldry/zephyr:base
  ├── /opt/spack_store/install_tree (~22 GB)
  │     Compiled packages + .spack-db index
  ├── /opt/spack_store/._view (~400 MB)
  │     Unified view directory (symlinks to install_tree)
  ├── /opt/spack_store/view → ._view/<hash>/ (symlink)
  ├── /opt/spack_store/misc_cache (~700 KB)
  ├── /opt/spack_env/default/spack.yaml + spack.lock
  ├── Reindexed Spack DB: spack reindex
  ├── Labels: sygaldry.spack.baked=true
  └── EXCLUDED: build_stage (~5.5 GB), source_cache (~14 GB)

Stage 3: MLSys Images (sygaldry/zephyr:{vllm,sglang,...})     ~38-40 GB
  FROM sygaldry/zephyr:spack
  ├── /opt/mlsys-envs/<env>/ (UV venvs, 500 MB - 2 GB each)
  ├── Shell integration in /home/kvothe/.bashrc
  ├── Labels: sygaldry.mlsys.baked=true, sygaldry.mlsys.env=<name>
  └── ENV: SYGALDRY_MLSYS_VENV_ROOT, SYGALDRY_MLSYS_ENV
#+end_example

** Spack Snapshot Dockerfile (=spack_snapshot.dockerfile=)

The snapshot dockerfile uses BuildKit named contexts to access the host
Spack store without copying it into the build context:

#+begin_example
DOCKER_BUILDKIT=1 docker build \
  -f container/spack_snapshot.dockerfile \
  --build-context spack_store=/mnt/data_infra/.../spack_store \
  -t sygaldry/zephyr:spack .
#+end_example

Key operations in the dockerfile:

1. =COPY --from=spack_store install_tree /opt/spack_store/install_tree= (~22 GB)
2. =COPY --from=spack_store ._view /opt/spack_store/._view= (~400 MB)
3. =COPY --from=spack_store misc_cache /opt/spack_store/misc_cache= (~700 KB)
4. Create view symlink: =ln -sfn /opt/spack_store/._view/<hash>/ /opt/spack_store/view=
5. Create empty =build_stage= and =source_cache= (so Spack doesn't error)
6. Re-COPY =pkg/zephyr= as =/opt/spack_env/default= (with =spack.lock=)
7. Re-COPY entrypoints and override files
8. =spack reindex= to rebuild the database from copied install_tree
9. Set label =sygaldry.spack.baked=true=

=build_stage= (5.5 GB) and =source_cache= (14 GB) are intentionally excluded.
They are only needed during compilation and waste ~20 GB of image space.

#+begin_example

   ├── Authenticate to registry (GITHUB_TOKEN for GHCR)

** Design Principles

*** P3.1: Exclude Ephemeral Build Artifacts

=build_stage= and =source_cache= are excluded from the snapshot.  They save
~20 GB of image space and are only needed during compilation.

*** P3.2: Reindex After COPY

=spack reindex= is mandatory after COPYing the install tree.  The database
(.spack-db) contains absolute paths and timestamps that may be stale after
the copy.  Reindexing rebuilds the database from the actual installed files.

*** P3.3: View Symlink, Not Copy

The view is a symlink tree (=/opt/spack_store/._view/<hash>/=) with the
top-level symlink =/opt/spack_store/view= pointing to it.  The snapshot
dockerfile recreates this symlink dynamically.

*** P3.4: Verification Before Promotion

No image is pushed to the registry until it passes T1-T7.  The =--no-verify=
flag exists for development iteration only.

* Pillar 4: Spack Staging Mechanism
:PROPERTIES:
:CUSTOM_ID: staging
:END:

** Problem Statement

Adding or upgrading a Spack spec can trigger cascading rebuilds that destroy
hours of compilation work.  Operators need a way to evaluate changes safely
before committing them to the production environment.

** Architecture

*** Two-Tool Pipeline

The staging mechanism consists of two tools that work in sequence:

**** Tool 1: =zephyr_concretize_analyze.py= -- Analysis Only

This tool concretizes in an isolated staging directory and reports which
hashes are missing from the installed tree.  It NEVER runs =spack install=.

Input: source env directory + optional additional specs.
Output: JSON report with concretized nodes, missing nodes, forbidden matches.

#+begin_example
Arguments:
  --source-env-dir    Source env (default: /workspace/pkg/zephyr)
  --stage-root        Base dir for staging (default: /tmp/zephyr_concretize_staging)
  --spec              Additional spec to add (repeatable)
  --forbidden-regex   Regex for packages that must not be missing
  --output-json       Path for JSON report
  --keep-stage        Retain staging directory
  --allow-deprecated  Allow deprecated package versions
#+end_example

Control flow:

#+begin_example
1. Copy source env files to staging directory:
   ├── spack.yaml (or spack_src.yaml → spack.yaml)
   └── spack.lock (if exists)
2. If --spec provided: spack add <spec> in staging env
3. spack concretize --force [--deprecated]
4. For each root spec: spack spec -j <spec> → parse JSON nodes
5. spack find --json → get installed hashes
6. Compute: missing = concretized - installed
7. Flag forbidden: regex match on missing package names
8. Emit JSON report
#+end_example

JSON report structure:

#+begin_src json
{
  "source_env_dir": "/workspace/pkg/zephyr",
  "stage_dir": "/tmp/.../run-XXXXXX",
  "concretization_success": true,
  "forbidden_regex": "(py-torch|py-jax|py-jaxlib|torch|jax|jaxlib|llvm)",
  "totals": {
    "concretized_nodes": 347,
    "installed_nodes_matched": 342,
    "missing_nodes": 5,
    "forbidden_missing_nodes": 0
  },
  "missing": [
    {
      "name": "py-soundfile",
      "version": "0.10.3.post1",
      "hash": "abc123...",
      "forbidden_match": false,
      "origin_specs": ["py-soundfile@0.10.3.post1"]
    }
  ]
}
#+end_src

**** Tool 2: =zephyr_stage_spack.sh= -- Analysis + Guarded Install

This tool wraps the analyzer and conditionally proceeds to install.

#+begin_example
Input:
  --source-yaml     Source manifest (default: /workspace/pkg/zephyr/spack_src.yaml)
  --spec            Spec to analyze (repeatable)
  --python-import   Module to import for verification (repeatable)
  --forbidden-names CSV of forbidden package names

Output directory: outputs/spack_stage/<run_id>/
  ├── source_env/       Copy of source manifest
  ├── analyze_stage/    Concretization staging directory
  └── logs/
      ├── concretize_report.json
      ├── new_requirements.txt
      ├── final_status.json
      ├── install.log
      ├── verify_pkg_zephyr.log
      ├── verify_gpu.log
      └── verify_imports.log
#+end_example

Control flow:

#+begin_example
1. Copy source YAML to staging
2. Run zephyr_concretize_analyze.sh → concretize_report.json
3. Extract staging env path from report
4. Generate new_requirements.txt from missing packages
5. FORBIDDEN CORE GUARD:
   ┌──────────────────────────────────────────────────────────┐
   │ Parse missing list from report.                          │
   │ Filter by forbidden names (default: py-torch, py-jax,   │
   │   py-jaxlib, torch, jax, jaxlib, llvm).                 │
   │ If ANY forbidden package is missing → exit 10.           │
   │ Production environment remains untouched.                │
   └──────────────────────────────────────────────────────────┘
6. spack install in staging env → install.log
7. spack env view regenerate → append to install.log
8. Verify (if --no-gpu-verify not set):
   ├── pkg/zephyr/verify.sh --require-gpu → verify_pkg_zephyr.log
   └── verify-gpu.sh entrypoint → verify_gpu.log
9. Verify explicit Python imports (if --python-import):
   └── Python import test → verify_imports.log
10. Write final_status.json: ok or failed + step + message
#+end_example

** Isolation Boundaries

| Resource           | Production Env    | Staging Env                    | Mutation Risk |
|--------------------+-------------------+--------------------------------+---------------|
| =spack.yaml=         | =pkg/zephyr/=       | =outputs/spack_stage/<id>/=      | None (copied) |
| =spack.lock=         | =pkg/zephyr/=       | Generated in staging           | None          |
| Install tree       | =/opt/spack_store/= | Shared (new pkgs install here) | Additive only |
| Source/build cache | =/opt/spack_store/= | Shared                         | Additive only |
| View               | Production view   | Staging-specific view          | None          |
| Logs               | N/A               | =<run_id>/logs/=                 | None          |

The install tree is intentionally shared.  Staging installs NEW packages into
the same tree that production uses.  This is safe because Spack packages are
content-addressed (each package lives at a unique hash path).  Installing
new packages does not modify existing ones.

** Exit Codes

| Code | Meaning                                     |
|------+---------------------------------------------|
|    0 | Staging succeeded, all verifications passed |
|    2 | Concretization analysis failed              |
|    3 | Failed to generate new requirements list    |
|   10 | Forbidden core guard triggered              |
|   11 | =spack install= failed                        |
|   12 | =spack env view regenerate= failed            |
|   13 | =pkg/zephyr/verify.sh= failed                 |
|   14 | =verify-gpu.sh= failed                        |
|   15 | Explicit Python import verification failed  |

** Design Principles

*** P4.1: Read-Only Production Files

Staging never modifies production =spack.yaml= or =spack.lock=.  All changes
happen in an isolated directory under =outputs/spack_stage/=.

*** P4.2: Forbidden Core Guard Exits Hard

Exit code 10 is a clear signal: the operator's proposed change requires
rebuilding a core package.  This is not an error to retry -- it requires a
conscious decision to proceed with a full build.

*** P4.3: Shared Install Tree is Safe

Content-addressed storage means new packages get their own hash directories.
Existing packages are never modified by new installs.  The only risk is disk
space consumption.

*** P4.4: Machine-Readable Reports

All artifacts are JSON or line-delimited text.  =final_status.json= provides a
single-file summary that agents can parse to determine pass/fail without
reading logs.

* Pillar 5: Spack+UV Package Synergy
:PROPERTIES:
:CUSTOM_ID: spack-uv-synergy
:END:

** Problem Statement

Users need to install Python packages (transformers, vllm, sglang, datasets)
that depend on PyTorch and NumPy.  If UV (the fast Python package installer)
is allowed to resolve these dependencies freely, it will:

1. Pull in pip copies of =torch=, =numpy=, =triton= that shadow the Spack versions.
2. Pull in =nvidia-cublas-cu12=, =nvidia-cudnn-cu12=, etc. that conflict with
   the Docker base image's CUDA.
3. Result in undefined-symbol crashes, CUDA version mismatches, and subtle
   numerical differences.

The synergy layer ensures UV can install application packages while treating
the Spack-provided packages as immutable system dependencies.

** Three-Tier Package Ownership Model

#+begin_example
┌────────────────────────────────────────────────────────────────────────┐
│ Tier 3: UV Application Packages                                       │
│   transformers, tokenizers, accelerate, vllm, sglang, datasets        │
│   Installed into /tmp/test-venv or /opt/mlsys-envs/<env>              │
│   Authority: per-project requirements.txt or YAML env definition      │
├────────────────────────────────────────────────────────────────────────┤
│ Tier 2: Spack Core ML/Scientific Packages (IMMUTABLE at UV time)      │
│   torch, torchvision, torchaudio, jax, jaxlib, triton                 │
│   numpy, scipy, scikit-learn, numba, llvmlite                         │
│   matplotlib, pandas, soundfile, jupyterlab                           │
│   Authority: container/spack_owned_packages.conf                      │
├────────────────────────────────────────────────────────────────────────┤
│ Tier 1: Docker CUDA/NVIDIA Runtime (FORBIDDEN to UV)                  │
│   libcuda.so, libcudnn.so, libnccl.so                                 │
│   nvidia-cublas-cu12, nvidia-cudnn-cu12, etc. (pip names)             │
│   Authority: Docker base image + container/nvidia_overrides.txt       │
└────────────────────────────────────────────────────────────────────────┘
#+end_example

** Enforcement Mechanisms

*** Mechanism 1: Build Isolation Bypass (=UV_NO_BUILD_ISOLATION_PACKAGE=)

The environment variable is populated from =spack_owned_packages.conf=:

#+begin_example
UV_NO_BUILD_ISOLATION_PACKAGE="torch,torchvision,torchaudio,jax,jaxlib,triton,
  numpy,scipy,scikit-learn,numba,llvmlite,matplotlib,pandas,soundfile,
  jupyterlab,transformer-engine-torch"
#+end_example

This tells UV: "Do not create an isolated build environment for these packages.
They are already available as system packages."  Without this, UV would try to
download and compile PyTorch from source if a dependency lists it as a build
requirement.

*** Mechanism 2: Spack Constraint File (generated at install time)

=uv-install.sh= generates a constraint file by querying Spack-owned packages:

#+begin_src python
import importlib.metadata as md
spack_owned = {"torch", "numpy", "scipy", ...}  # from spack_owned_packages.conf
for dist in md.distributions():
    name = dist.metadata.get("Name")
    if name and name.lower() in spack_owned:
        version = re.sub(r'\+.*$', '', dist.version)  # strip local tags
        print(f"{name}=={version}")
#+end_src

Output example:

#+begin_example
torch==2.9.0
torchvision==0.24.0
numpy==2.3.4
scipy==1.16.3
#+end_example

This file is passed as =--constraint= to =uv pip install=, which forces UV to
accept these exact versions rather than resolving newer ones.

The local-version-tag stripping (=re.sub(r'\+.*$', '', version)=) is necessary
because Spack sometimes appends build hashes (e.g., =2.9.0+eaa9e4e=) that
UV's PEP 440 parser rejects.

*** Mechanism 3: NVIDIA Override File (=nvidia_overrides.txt=)

Uses the "impossible marker" pattern to make nvidia pip packages unresolvable:

#+begin_example
nvidia-cublas-cu12; sys_platform == 'never'
nvidia-cudnn-cu12; sys_platform == 'never'
nvidia-nccl-cu12; sys_platform == 'never'
# ... 15+ nvidia-* packages for CUDA 11 and 12
#+end_example

=sys_platform == 'never'= is never true, so UV treats these packages as
if they don't exist.  When vllm or sglang declare =nvidia-cublas-cu12= as a
dependency, UV silently skips it.

Also includes workarounds:

#+begin_example
# Fix broken Spack dist-info metadata
python-dateutil>=2.8.2     # Spack reports 0.0.0, actual is 2.8.2

# Relax tight numpy pin from megatron-core
numpy>=2.0.0               # megatron pins <2.0.0, Spack has 2.3.4
#+end_example

*** Mechanism 4: LLM Serving Overrides (=llm_serving_overrides.txt=)

Opt-in override file for packages like vLLM and sglang that pin exact versions:

#+begin_example
torchvision>=0.20.0     # vLLM pins exact torchvision per release
torchaudio>=2.9.0       # sglang pins exact torchaudio
numba>=0.60.0           # vLLM pins numba==0.61.2
triton>=3.4.0           # PyPI metadata says 3.5.0, Spack has 3.4.0
soundfile>=0.10.0       # sglang pins 0.13.1, Spack has 0.10.3.post1
torch>=2.9.0; sys_platform == 'never'   # Block pip torch entirely
#+end_example

The =torch; sys_platform == 'never'= line is the nuclear option: it
prevents UV from resolving pip-distributed torch under any circumstances,
forcing the system to use the Spack-compiled version.

** UV Venv Creation (=uv-install.sh=) Detailed Flow

#+begin_example
1. FIND Spack Python:
   /opt/spack_store/view/bin/python3 (preferred)
   $(command -v python3) (fallback)

2. READ spack_owned_packages.conf:
   /opt/container_entrypoints/spack_owned_packages.conf (preferred)
   Hardcoded fallback list (if file not found)

3. SET UV_NO_BUILD_ISOLATION_PACKAGE from conf file

4. LOCATE nvidia_overrides.txt:
   /opt/container_entrypoints/nvidia_overrides.txt (preferred)
   Relative to entrypoints directory (fallback)

5. CREATE venv:
   uv venv --python $SPACK_PY --system-site-packages $VENV_DIR

6. INJECT .pth file:
   echo "/opt/spack_store/view/lib/python3.13/site-packages" > \
     $VENV_DIR/lib/python3.13/site-packages/spack-view.pth

7. GENERATE constraint file:
   $SPACK_PY -c "...enumerate spack-owned versions..." > /tmp/spack-constraints.txt

8. INSTALL:
   uv pip install \
     --constraint /tmp/spack-constraints.txt \
     --override nvidia_overrides.txt \
     [--override $UV_EXTRA_OVERRIDES] \
     "$@"
#+end_example

The =.pth= file in step 6 is critical.  =--system-site-packages= alone makes
the system Python's site-packages visible, but the Spack view's site-packages
are at a different path than the system Python.  The =.pth= file explicitly
adds the Spack view path to =sys.path=.

** Verification (T8.1-T8.8)

=container/verify_uv_layering.sh= validates the entire synergy:

| Test | What it does                                                         | Blocking? |
|------+----------------------------------------------------------------------+-----------|
| T8.1 | Create UV venv, install transformers + tokenizers + accelerate       | Yes       |
| T8.2 | Verify torch, torchvision, torchaudio, jax, numpy, scipy, triton    | Yes       |
|      | all resolve from =/opt/spack_store/view= (not pip)                   |           |
| T8.3 | Verify transformers, tokenizers, accelerate from UV venv (not Spack) | Yes       |
| T8.4 | No =nvidia-*= packages installed outside Spack view                  | Yes       |
| T8.5 | torch CUDA matmul + HF tokenizer load after UV layering              | Yes (GPU) |
| T8.6 | vLLM: install, provenance, no nvidia pip, ABI safety                 | Serving   |
| T8.7 | datasets: install in separate venv                                   | Non-block |
| T8.8 | sglang: install, provenance, no nvidia pip, ABI safety               | Serving   |

ABI safety checks (T8.6, T8.8) detect hard-fail patterns:
- =undefined symbol= -- wrong .so version loaded
- =libnvJitLink= -- CUDA JIT linker mismatch
- =libcusparse= -- cuSPARSE version mismatch

** Design Principles

*** P5.1: Spack Packages Are Immutable at UV Time

UV never installs, upgrades, or rebuilds Spack-owned packages.  This is
enforced by three independent mechanisms that provide defense-in-depth.

*** P5.2: NVIDIA Pip Packages Are Forbidden

Mixing pip-distributed CUDA libraries with the Docker base image's CUDA
causes crashes.  The override file makes them unresolvable.

*** P5.3: System Site-Packages + .pth

The combination of =--system-site-packages= and the =.pth= file creates a
transparent bridge: UV venvs can "see" all Spack packages without copying
them.  This means =import torch= in any UV venv resolves to the Spack-compiled
version.

*** P5.4: Constraint File Uses Spack-Owned Packages Only

The constraint file is generated ONLY from packages listed in
=spack_owned_packages.conf=, not from all packages in the Spack view.  This
prevents stale transitive dependencies (e.g., =datasets==0.0.9= from a broken
dist-info) from poisoning the UV resolver.

*** P5.5: Override Files Are Composable

The base =nvidia_overrides.txt= is always applied.  Additional overrides
(=llm_serving_overrides.txt=) are opt-in via =UV_EXTRA_OVERRIDES=.  This
allows different environments to have different relaxation policies.

*** Image Build Pipeline

*** YAML Environment Schema (=zephyr-mlsys/v1=)

** MLSys Dockerfile (=mlsys_venv.dockerfile=)

Key implementation details:

#+begin_example
FROM ${SPACK_SNAPSHOT_IMAGE}    # Stage 2 as base

# Bake skill scripts and env definitions
COPY skills/zephyr-mlsys-env /opt/sygaldry/skills/zephyr-mlsys-env

# Update entrypoints (ensure MLSys auto-activation code is present)
COPY container/entrypoints/{default,run-job,uv-install}.sh /opt/container_entrypoints/

# Patch broken dist-info (python-dateutil 0.0.0 → 2.8.2)
RUN sed -i 's/^Version: 0.0.0$/Version: 2.8.2/' \
    /opt/spack_store/view/lib/python3.13/site-packages/python_dateutil-0.0.0.dist-info/METADATA

# Build UV venvs (BuildKit cache mount avoids baking download cache)
RUN --mount=type=cache,target=/opt/uv_cache,uid=1000,gid=1000 \
    uv-env-build.sh ${MLSYS_ENV} --no-validate --venv-root /opt/mlsys-envs

# Shell integration: .bashrc auto-activates venv + mlsys-activate function
RUN cat >> /home/kvothe/.bashrc <<'BASHRC_EOF'
...re-activation + mlsys-activate function...
BASHRC_EOF

# Metadata
ENV SYGALDRY_MLSYS_VENV_ROOT=/opt/mlsys-envs
ENV SYGALDRY_MLSYS_ENV=${MLSYS_ENV}
LABEL sygaldry.mlsys.baked="true"
LABEL sygaldry.mlsys.env="${MLSYS_ENV}"

persistent download cache across builds without baking ~2 GB of cached wheels

** Design Principles

*** P6.1: Snapshot as Sole Base

Every MLSys image uses =sygaldry/zephyr:spack= as its FROM.  No MLSys image
may run =spack install=.  They only add UV venvs.

*** P6.2: No GPU at Build Time

Docker builds have no GPU.  Validation happens post-build.  This allows
building on CPU-only CI and validating on GPU nodes.

*** P6.3: Multi-Venv for Conflicting Packages

When packages have incompatible transitive dependency graphs (vLLM vs sglang),
create separate venvs rather than fighting the resolver.  The
=mlsys-activate <name>= function provides seamless switching.

*** P6.4: Hard-Fail ABI Detection

Patterns like =undefined symbol= and =libnvJitLink= in import errors indicate
a fundamental ABI mismatch between the UV-installed package and the Spack core.
These are treated as hard failures that block image promotion.

*** P6.5: Broken Dist-Info Patching

The dockerfile patches =python-dateutil= dist-info from 0.0.0 to 2.8.2.  This
is a known Spack issue where the dist-info metadata does not match the actual
installed version.  Without this patch, UV refuses to resolve any package
that requires =python-dateutil>=2.8.2=.

** Security

*** Container Security

- *Dynamic user mapping*: Container user =kvothe= matches exact host UID/GID.
  Automatic conflict resolution if UID/GID already exists in image.
- *Minimal attack surface*: Ubuntu 24.04 LTS base, headless, no GUI components.
- *Network*: Host network access only when required (=--net=host=).
- *Resource limits*: CPU/memory constraints available via Docker.
- *Non-root execution*: =sudo= available for development convenience only.

*** Dependency Security

- *Trusted sources*: Official Spack packages and verified repositories.
- *Isolation*: Sandboxed builds prevent supply chain attacks.
- *Reproducible builds*: Lockfile-pinned installs (=spack.lock=) for cryptographic verification.

*** Access Control

- *Volume mounts*: Read-only mounts where possible (e.g., =/opt/sygaldry= in multi-repo mode).
- *Secrets management*: Environment variables and mounted files; never baked into images.
- *GPU access*: Controlled NVIDIA runtime exposure; no CPU-only mode.
- *Builder role gate*: Only =SYGALDRY_BUILD_ROLE=builder= can mutate Spack store.

** Concurrency: Lease Model

The launcher writes advisory GPU leases to prevent concurrent GPU-intensive
operations from interfering with each other:

#+begin_example

owner=sygaldry
run_id=run-20260216-143022-12345
pid=12345
created_epoch=1739712622
expires_epoch=1739734222    # 6-hour TTL
#+end_example

Lease behavior controlled by =--lease-mode=:
- =off=: ignore leases
- =warn=: print warning if lease exists, continue
- =enforce=: fail if active lease exists

3. Warn on deprecated env vars (SYGALDRY_SPACK_STORE, etc.)
4. Check requirements: Docker daemon, NVIDIA runtime
5. Setup host directories: create all directories in the storage layout
6. Build container image (auto/always/never policy)
7. Detect baked Spack (docker inspect for sygaldry.spack.baked label)
8. Resolve mount paths (realpath all host directories)
9. Resolve entrypoint path (baked vs host-mounted)
10. Acquire GPU lease (if lease mode != off)
11. Build docker run args:

    ├── --net=host --ipc=host
    ├── --user=<host-uid>:<host-gid>

    ├── --runtime=nvidia --gpus=all
    ├── Environment variables (30+ injected)
    └── --entrypoint=<resolved-path>
12. docker run $ARGS $IMAGE $PASSTHROUGH_ARGS
13. Release GPU lease
14. Exit with container's exit code

** R8: Temporal-Driven Spack Builds
:PROPERTIES:
:CUSTOM_ID: r8-temporal-builds
:END:

*** Problem

#+begin_example

  - id: preflight
    type: command
    command: container/verify_preflight.sh --smoke

  - id: spack-build
    type: container_job
    depends_on: [preflight]
    container_job:
      project_id: sygaldry
      entrypoint: spack-build.sh
      gpu: true
    timeout_seconds: 28800    # 8 hours
    retry:
      max_attempts: 3
      backoff_seconds: 600

  - id: gpu-verify
    type: container_job
    depends_on: [spack-build]
    container_job:
      project_id: sygaldry
      entrypoint: verify-gpu.sh
      gpu: true

  - id: snapshot
    type: command
    depends_on: [gpu-verify]
    command: container/snapshot_spack.sh --no-push

  - id: snapshot-verify
    type: command
    depends_on: [snapshot]
    command: container/verify_snapshot.sh ${{ steps.snapshot.outputs.tag }}
#+end_example

Benefits over the shell scripts:
- *Error classification*: Temporal activities can parse build logs for known
  failure patterns and choose remediation (clear build cache, relax constraints,
  notify human).
- *Monitoring*: Temporal UI at =localhost:8233= shows live step progress, duration,

- *Persistence*: Build history survives process restarts.
- *Extensibility*: Adding steps (MLSys build, push, notification) is a YAML edit.

- [ ] Spack build pipeline runs end-to-end via Temporal
