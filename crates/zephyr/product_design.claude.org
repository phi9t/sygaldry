#+TITLE: Zephyr CLI — Product Design Review
#+AUTHOR: Claude (product design analysis)
#+DATE: 2026-02-21
#+STARTUP: showall

This document evaluates the Zephyr CLI from the perspective of an engineer or
ML researcher using it daily. It is not a technical reference (see
=foundation.org=) but a UX-focused critique: what's delightful, what causes
friction, and where the tool should evolve.

* Design Philosophy

The Zephyr CLI is built around a single binary that operates in two distinct
runtime contexts: *host orchestration* (launching containers, managing jobs,
staging Spack environments) and *container init* (setting up Spack, verifying
GPUs, installing packages). A single =RuntimeContext= enum detected via
=SYGALDRY_IN_CONTAINER=1= routes all dispatch — there is no separate binary
for each side.

The configuration surface follows zero-config defaults with *progressive
disclosure*. Out of the box, =sygaldry shell= works with sensible defaults
(image =sygaldry/zephyr:base=, lease mode =warn=, cache profile =shared=,
build policy =auto=). Power users can override any of 30+ env vars, and CLI
flags take precedence over env vars.

Error handling uses a *fail-safe cascade* pattern throughout. The Spack init
sequence in =full_init()= is deliberately non-fatal — if =init_spack()= fails,
it tries =activate_env()=; if that fails, it falls back to =ensure_view_fallback()=
which directly injects the Spack view into =PATH=, =PYTHONPATH=, and
=LD_LIBRARY_PATH=. The container keeps working even when Spack itself is broken.

Source: =context.rs=, =config.rs=, =cli.rs=, =container/spack.rs:140-156=

* First-Run Experience

** The bin/sygaldry Wrapper

The user's first touchpoint is =bin/sygaldry=, a bash wrapper that resolves
=SYGALDRY_HOME= from its own location, then checks for the Rust binary at
=crates/zephyr/target/release/zephyr=. If present, it execs directly into
Rust. Otherwise it falls back to a bash dispatcher covering every subcommand.
The upgrade path is invisible: compile once, every subsequent invocation is Rust.

Source: =bin/sygaldry:32-35=

** Auto-Build and Welcome

=sygaldry shell= uses =BuildPolicy::Auto= — if the Docker image doesn't exist
locally, it builds automatically. No manual =docker build= required.

The default entrypoint prints a context-aware welcome banner adapted to the
active MLSys variant (=SYGALDRY_MLSYS_ENV=). It shows quick commands
(=gpu-test=, =jax-test=, =spack-env-activate=), environment paths, and
for =llm-serving-all=, a hint for switching between HF/vLLM/SGLang venvs.

The welcome banner is context-aware because =full_init()= calls
=mlsys_venv::activate()=, which auto-activates pre-baked Python venvs based
on =SYGALDRY_MLSYS_ENV=. It supports target-specific variants via
=SYGALDRY_MLSYS_TARGET= with alphabetical fallback when no target matches.
This is why the banner can show the active venv path and variant-specific hints.

An auto-generated RC file (=/tmp/.zephyr_shellrc=) provides shell aliases:
=gpu-test=, =jax-test=, =spack-build=, and an =hf-dataset()= function.
It sources =~/.bashrc= first so personal customizations are preserved.

*Friction:* The welcome banner advertises =spack-env-activate= as a quick
command, but =write_shell_rc()= does not create this alias. A new user who
types it gets "command not found" — a promise-vs-delivery gap in the first
30 seconds.

Source: =container/entrypoint.rs:354-407=, =container/mlsys_venv.rs:7-43=

* Error Experience

** What Makes It Delightful

*** The WithHint Pattern

Every actionable error carries a remediation hint via =WithHint { message, hint }=:

#+begin_example
Spack setup script not found at /opt/spack_src
HINT: Are you inside the container? Use 'zephyr shell' to launch one.
#+end_example

37 distinct hint sites across 13 source files cover missing commands, missing
resources, permission issues, path problems, and forbidden operations. The
=with_hint()= constructor makes adding guidance trivial at every error site.

Source: =error.rs:67-89=

*** IoResultExt and Typed Variants

The =IoResultExt= trait adds =.with_path()= to =std::io::Result=, so I/O errors
always include the file path (not bare "No such file or directory").

18 error variants carry structured context: =ImageNotFound { image }=,
=CudaVersionTooOld { host, required }=, =LeaseConflict { resource, lease_file }=,
=JobNotFound { project_id, job_name }=, =CommandFailed { command, code }=, etc.

Source: =error.rs:8-78=

** Where It Falls Short

*** No --verbose / ZEPHYR_LOG_LEVEL

There is no way to increase log verbosity at the CLI level. When something
fails silently in the 10-step launch pipeline, the user has no recourse
beyond reading source code. The =stage= subcommand has =--verbose=, but
this is not available for =shell=, =run=, or =job= commands.

*** UV Constraint Conflicts

When =uv pip install= fails due to Spack constraint conflicts, the error
is a raw pip-resolver dump. The CLI doesn't parse or reformat it. A user
seeing "no matching version for torch==2.9.0+eaa9e4e" has no idea this
means "Spack already provides torch, don't install it from PyPI."

Source: =error.rs:27-31=

* Day-to-Day Workflows

** Container Launch (=sygaldry shell= / =sygaldry --repo .=)

The launch pipeline in =host/launcher.rs:12-71= runs 10 steps: pre-flight
checks → CUDA validation → host dir setup → image build/check → Spack bake
detection → entrypoint resolution → lease acquisition → Docker arg
construction (60+ args) → docker run → lease release (Drop).

The lease system has three modes: *off* (no lease file created), *warn*
(print a warning and continue), and *enforce* (block launch with
=LeaseConflict= error). The default is =warn= with a 6-hour TTL. The
=LeaseGuard= removes the file on drop, so normal exits always clean up.

*Friction:* A new team member runs =sygaldry shell= for the first time. The
image isn't cached, so Docker builds it — but for 3 minutes, nothing is
printed. They ctrl-C thinking it hung. Only two messages appear: "Starting
container launcher..." and "docker run (entrypoint=default)". Steps 1-8 run
silently. Multi-repo mode gives no mount confirmation of what was mounted where.

When a lease conflict is detected in =warn= mode, the message says "Resource
lease exists (gpu-all) at /path/to/lease" — but the user can't tell if it's
their own stale lease from yesterday or a colleague's active job. The lease
file already stores owner, PID, and expiry fields — but the warning message
doesn't read them. This makes the "lease conflict details" improvement below
a read-and-format task, not new infrastructure.

Source: =host/launcher.rs=, =host/lease.rs:62-107=

** Job Management (=sygaldry job run/status/tail/stop/health=)

Background jobs are a well-designed subsystem with five commands:

| Command  | What it does                                    |
|----------+-------------------------------------------------|
| =run=    | Launch container in background via =nohup=      |
| =status= | Read last line of =.status= file               |
| =tail=   | Last N lines of JSONL log (default 80)          |
| =stop=   | Send SIGTERM via =libc::kill()=                 |
| =health= | PID liveness check + status file check          |

*Delightful touches:*
- =latest-<job_name>= symlinks in the =runs/= directory for quick access
  without remembering run IDs
- JSONL structured logs with =ts=, =event=, =job=, =msg= fields — grep-friendly
  and machine-parseable
- Heartbeat thread writes =PROGRESS= to status file and =progress= event
  to JSONL every 5 minutes — reliable liveness signal
- =run= prints a clear summary: job name, project ID, run ID, PID, all file paths

*Friction:* A researcher starts 4 training jobs on Friday afternoon. On Monday,
they want to check which ones finished — but there's no =job list=. They resort
to =ls runs/ | grep pid=.

Source: =host/job.rs:29-314=, =container/entrypoint.rs:244-322=

** GPU Verification (=sygaldry verify-gpu=)

The GPU check embeds a Python script via =include_str!()= — no loose files to
manage, no "script not found" errors. The script runs a dual-framework
validation:

1. *PyTorch CUDA:* =torch.cuda.is_available()=, device count >= 1,
   64x64 =matmul= on GPU
2. *JAX GPU:* =jax.devices()= enumeration, GPU platform filter,
   64x64 =jnp.matmul=

Failures from both frameworks are collected and reported together rather than
short-circuiting on the first error. The Rust wrapper sets up Spack paths
before running the script, with the full init → activate → view fallback
cascade. This means GPU checks work even when Spack env activation is broken.

*Friction:* Both checks print results to stderr, not stdout, which is correct
for a validation tool but surprising when piping output. The check takes 5-10
seconds (JAX JIT compilation) with no progress indication.

Source: =container/gpu_check.rs:1-30=, =scripts/gpu_check.py=

** Package Installation (=sygaldry entrypoint uv-install=)

Solves layering pip packages on a Spack-built Python stack: creates a venv
with Spack's Python, generates constraint files (prevents overriding torch/
numpy/jax), applies NVIDIA overrides, and injects a =.pth= file pointing
to the Spack view's =site-packages=. The =.pth= injection makes Spack
packages visible without modifying =PYTHONPATH= — tools like pytest and
mypy see the full package set.

*Friction:* The =.pth= injection is invisible by design, which is good for
normal use — but when debugging import issues (wrong torch version, missing
CUDA symbols), there's no =zephyr explain-imports= or similar diagnostic.

Source: =container/uv_install.rs=

** HuggingFace Downloads (=sygaldry entrypoint hf-download=)

Auto-creates a dedicated venv at =/opt/uv_cache/venvs/hf-download=, checks
if deps are already present before reinstalling. Uses =snapshot_download()=
for models and =load_dataset()= for datasets. =HF_HOME= defaults to
=/opt/hf_cache=.

Source: =container/hf_download.rs=

** LoRA Fine-Tuning Setup (=sygaldry entrypoint hf-lora-setup=)

Creates a Spack-backed venv for HuggingFace fine-tuning without overriding
the Spack-built torch. Installs transformers, datasets, peft, and accelerate
(peft/accelerate with =--no-deps= to avoid pulling a second torch). Generates
an =hf-lora-python= wrapper script that blends the venv's site-packages with
Spack's — so =import torch= resolves to the CUDA-built Spack version while
=import peft= resolves to the venv. Package versions are configurable via
env vars (=HF_TRANSFORMERS_VERSION=, etc.) with tested defaults.

Source: =container/entrypoint.rs:143-226=

** Spack Staging (=sygaldry stage=)

The staging pipeline orchestrates a full Spack concretize-install-verify
sequence across 7 steps, each with a distinct exit code (2-15):

| Exit | Step                        | What fails               |
|------+-----------------------------+--------------------------|
|    2 | Concretization analysis     | =concretize_report.json=   |
|    3 | New requirements generation | JSON parse or write      |
|   10 | Forbidden guard check       | Core packages in missing |
|   11 | =spack install=               | Build failure            |
|   12 | View regeneration           | View link failure        |
|   13 | pkg/zephyr verify           | Spack env broken         |
|   14 | GPU verification            | CUDA test failure        |
|   15 | Python import verification  | Missing modules          |

Machine-readable exit codes make CI integration straightforward — a pipeline
can branch on the specific failure step.

=final_status.json= records the complete run context: paths, specs, forbidden
names, and (on failure) the exact step and error message. This file is the
single source of truth for post-mortem analysis.

The forbidden guard prevents accidentally rebuilding core packages (torch,
jax, jaxlib, llvm) — these must come from the existing Spack store.

*Friction:* No step-by-step progress output. A staging run can take hours
(Spack builds are slow), and the user sees nothing until success or failure.
The =--verbose= flag exists but only affects the forbidden guard output.

Source: =host/staging.rs:80-252=

* Configuration UX

** Current State

Configuration flows through a clear precedence chain:

#+begin_example
CLI flags → env vars (ZEPHYR_X) → legacy env vars (SYGALDRY_X) → defaults
#+end_example

The =env_chain()= function reads the first non-empty value from a list of
env var names, making legacy migration transparent. Legacy vars trigger
deprecation warnings:

#+begin_example
[zephyr] DEPRECATED: SYGALDRY_SPACK_STORE set; prefer ZEPHYR_SHARED_SPACK_STORE
#+end_example

=sygaldry config show= (or =--print-effective-config=) dumps the resolved
configuration to stderr, including mode, IDs, cache paths, and the Spack
store host-to-container mapping. This is invaluable for debugging
"why is it using *that* directory?"

CLI flags override env vars for 5 key settings: project ID, run ID, repo
path, lease mode, and cache profile.

Source: =config.rs:106-128=, =config.rs:345-374=

** Friction Points

*** No Config File

A researcher who always uses =SYGALDRY_PROJECT_ID=llm-bench= and
=SYGALDRY_IMAGE=sygaldry/zephyr:spack-20260212= must export these in every
new terminal. All 30+ configuration options are env vars — excellent for CI/CD
but painful for personal defaults.

A =zephyr.toml= or =.zephyrrc= with layered precedence (file → env → CLI)
would eliminate this friction.

*** No Shell Completions

The CLI uses clap v4 with derive, which supports shell completion generation
via =clap_complete=. But this feature is not enabled — no bash/zsh/fish
completions are available. For a tool with 8 subcommands and 5 job actions,
tab completion would significantly reduce cognitive load.

Source: =Cargo.toml= (clap features: =["derive", "env"]=, no =clap_complete=)

* Design Vision: Delightful Improvements

** Quick Wins (small changes, high delight)

*** =job list= subcommand

Scan =projects/<id>/runs/= for PID files and symlinks, cross-reference
with status files, format a table (~80 lines, add =List= to =JobAction=).
Eliminates the most common "how do I see my jobs?" question from new users.

*** Shell completions

Add =clap_complete= to =Cargo.toml= and a =completions= subcommand (~20 lines).
Reduces the learning curve for a tool with 8 subcommands and nested actions.

*** Lease conflict details

Read the existing lease file to show owner PID, project ID, acquisition
timestamp, and expiry. The lease file already stores these fields — this is
a read-and-format task, not new infrastructure.

*** =--verbose= / =-v= flag for all commands

Global =-v= flag with per-step timing. Turns the 10-step launch pipeline from
a black box into a debuggable sequence. Currently only =stage= has =--verbose=.

** Medium Effort (significant UX improvement)

*** Progress indicators for long operations

Step counters for image build and staging pipeline. Currently both run
silently for minutes/hours. Even =[zephyr] [4/7] Installing packages...=
would be a significant improvement.

*** =zephyr.toml= config file

Layered: =~/.config/zephyr/config.toml= → project =.zephyr.toml= → env → CLI.
Eliminates the pain of exporting 3+ env vars for personal defaults.

*** Multi-repo mount summary

Print what was mounted after launch: repo path → container path, sygaldry (ro),
spack_store, shared caches. Currently the user gets no confirmation.

*** Structured UV constraint error output

Parse pip-resolver failures, identify the conflicting Spack package, and
suggest adding it to =spack_owned_packages.conf=. Currently raw resolver dump.

** Architectural (deeper changes)

*** =tracing= integration

Replace ad-hoc =eprintln!()= with the =tracing= crate: structured spans,
configurable output format (=ZEPHYR_LOG_FORMAT=), per-module verbosity,
and timing spans for performance analysis.

*** Interactive staging mode

Step-by-step progress with ETA estimates for =sygaldry stage=. Currently
the 7-step pipeline (which can take hours) runs silently until completion.

*** Plugin system for custom entrypoints

Currently 9 entrypoints are hardcoded in =container/entrypoint.rs:10-21=.
Auto-discover scripts in a directory to let teams add project-specific
entrypoints without modifying the Zephyr binary.

* Engineering Quality

** How Engineering Choices Affect UX

*** Test Coverage

283 tests (277 unit + 6 integration), all passing. The test suite uses an
*environment-adaptive* pattern: tests that depend on container resources
(Spack, GPU) detect their absence and adjust assertions accordingly, rather
than skipping entirely. This validates the same degraded conditions users hit
(no GPU, no Spack), ensuring fallback paths actually work.

Pure logic is extracted from subprocess-dependent code for unit testing:
- =parse_pid()= — tested without process spawning
- =generate_new_requirements()= — takes file paths, returns results, no Spack
- =check_forbidden_guard()= — operates on JSON values, not live environments
- =env_chain()= — tested with synthetic env vars

Tests that mutate process state (env vars) use =#[serial]= via =serial_test=,
preventing flaky parallel execution.

*** Module Architecture

The codebase splits into =host/= and =container/= modules, mirroring the
runtime context. Host-side code never calls container-side code, and vice
versa. Users never see host-side error messages when running inside the
container. The =context.rs= detection is the only bridge.

Path constants are centralized in =paths.rs=: 24 container paths and the
=HostLayout= struct with 22 fields for host directories. The
=required_dirs()= method returns all directories that must exist, and
=ensure_dirs()= creates them.

The single binary has no runtime Python/Go/Node dependency — 7 minimal Rust
crates (clap, serde, chrono, thiserror, which, libc, serde_json). You can
=scp= it to a server and it works.
