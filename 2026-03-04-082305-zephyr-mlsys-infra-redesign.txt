│ Plan to implement                                                            │

│ MLSys Build-Time Image System — Redesign                                     │
│                                                                              │
│ Context                                                                      │
│                                                                              │
│ The current system (build-mlsys.sh + launch-mlsys.sh +                       │
│ zephyr_mlsys_vendor.sh) works but                                            │
│ has three concrete complexity problems the user wants addressed:             │
│                                                                              │
│ 1. build-mlsys.sh is 398 lines mixing bash orchestration with embedded       │
│ Python YAML/TOML                                                             │
│ parsing — fragile, hard to test, hard to read.                               │
│ 2. Three separate override files (spack_owned_packages.conf,                 │
│ nvidia_overrides.txt,                                                        │
│ llm_serving_overrides.txt) in container_entrypoints/ are hard to discover    │
│ and understand.                                                              │
│ 3. Vendor directory + config.yaml setup (.codex-zephyr-mlsys/, verbose       │
│ config template)                                                             │
│ is friction-heavy.                                                           │
│                                                                              │
│ Additionally, two new capabilities are needed:                               │
│ - Build off any base image (Spack snapshot OR an existing mlsys image for    │
│ chaining)                                                                    │
│ - In-container scripts: a Docker ENTRYPOINT that activates the baked venv,   │
│ and an                                                                       │
│ in-container job runner script                                               │
│                                                                              │
│ The Spack-UV layering strategy itself (Spack owns torch/jax/llvm, UV layers  │
│ on top with                                                                  │
│ constraints) is proven and stays unchanged.                                  │
│                                                                              │
│ ---                                                                          │
│ Image Relationship: Zephyr Spack Base → MLSys                                │
│                                                                              │
│ sygaldry/zephyr:spack@sha256:abc...          ← Zephyr Spack base image       │
│ (60GB)                                                                       │
│ │  Built via: spack_snapshot.dockerfile                                      │
│ │  Contains: CUDA 12.9.1, torch 2.9.0, JAX 0.7.0, llvm, numpy, scipy         │
│ (Spack-managed)                                                              │
│ │  Baked at /opt/container_entrypoints/:                                     │
│ │    uv-install.sh, spack_owned_packages.conf,                               │
│ │    nvidia_overrides.txt, llm_serving_overrides.txt                         │
│ │                                                                            │
│ └── project-A/mlsys:latest@sha256:def...     ← MLSys image (repo-scoped,     │
│ +1-3GB)                                                                      │
│     │  Built via: build-mlsys.sh / _build_helper.py                          │
│     │  Adds on top of Spack base:                                            │
│     │    - apt packages (e.g. libsndfile1-dev, ffmpeg)                       │
│     │    - UV venv at /opt/repo-venv:                                        │
│     │        transformers, accelerate, datasets, peft ...                    │
│     │        (constrained to not re-install Spack packages)                  │
│     │    - /opt/mlsys-entrypoint.sh  (activates venv + exec)                 │
│     │    - /opt/mlsys-run-job.sh     (in-container job runner)               │
│     │                                                                        │
│     └── project-B/mlsys:latest@sha256:ghi...  ← Chained MLSys image          │
│         Built with project-A's image as base_image.                          │
│         Inherits all of A's venv + Spack packages.                           │
│         Adds its own apt packages and UV deps on top.                        │
│                                                                              │
│ Key invariant: uv-install.sh and the constraint files live in the Spack base │
│  image at                                                                    │
│ /opt/container_entrypoints/. Every MLSys image (direct or chained) inherits  │
│ them through the                                                             │
│ Docker layer chain — no re-vendoring needed in the generated Dockerfile. The │
│  COPY in the                                                                 │
│ generated Dockerfile is only for the two new in-container scripts            │
│ (entrypoint.sh,                                                              │
│ run-job.sh) that don't live in the Spack base yet.                           │
│                                                                              │

│ Design                                                                       │
│                                                                              │
│ What stays unchanged                                                         │
│                                                                              │

│ - container_entrypoints/uv-install.sh — the constraint-generation +          │

│ - Spack constraint chain: spack_owned_packages.conf → nvidia_overrides.txt → │
│  llm_serving_overrides.txt                                                   │
│ - image.lock format and image.lock-based launch pattern                      │
│ - Docker build using docker buildx build --load                              │
│                                                                              │
│ Change 1 — Split build script: bash wrapper + Python helper                  │
│                                                                              │
│ build-mlsys.sh (398 lines, bash + embedded Python) → two files:              │
│                                                                              │
│ bin/build-mlsys.sh (~120 lines, bash only):                                  │
│ - CLI arg parsing (--config, --force-rebuild, --no-cache)                    │
│ - Calls python3 "$(dirname "$0")/_build_helper.py" "$CONFIG_FILE"            │
│ "$BUILD_CTX_DIR"                                                             │
│ - Runs docker buildx build --load -t "$IMAGE_NAME" "$BUILD_CTX_DIR"          │
│ - Retrieves digest, writes image.lock                                        │
│                                                                              │
│ bin/_build_helper.py (NEW, ~220 lines, Python only):                         │
│ - Parses config.yaml using json/tomllib (no embedded YAML parser in bash)    │
│ - Extracts python deps from: inline packages:, requirements: file, or        │
│ pyproject: file                                                              │
│ ([project.dependencies] + optional-extras via tomllib, Py 3.11+ stdlib;      │
│ fallback to tomli)                                                           │
│ - Copies container/entrypoint.sh and container/run-job.sh into build context │
│  dir                                                                         │
│ - Generates Dockerfile in build context dir                                  │
│ - Prints IMAGE_NAME=<value> to stdout for the bash script to read            │
│                                                                              │
│ This makes all YAML/TOML parsing independently testable in Python.           │
│                                                                              │
│ Change 2 — Relax base_image restriction                                      │
│                                                                              │
│ Currently: hard-fail if base_image lacks @sha256: digest.                    │
│ New: accept any Docker image ref. If no digest found, print a warning        │
│ (reproducibility notice)                                                     │
│ but don't error. This enables:                                               │
│ - sygaldry/zephyr:spack@sha256:abc... — Spack snapshot (existing)            │
│ - your-project/mlsys:latest@sha256:abc... — chain from another mlsys image   │
│ - sygaldry/zephyr:spack — unpinned (warn only)                               │
│                                                                              │
│ Change 3 — In-container scripts (two new files)                              │
│                                                                              │
│ container/entrypoint.sh (NEW, ~25 lines):                                    │
│ Docker ENTRYPOINT baked into every built image. Activates the repo venv,     │
│ then exec "$@".                                                              │
│ #!/bin/bash                                                                  │
│ set -e                                                                       │
│ VENV="${MLSYS_VENV_PATH:-/opt/repo-venv}"                                    │
│ if [ -d "$VENV" ]; then                                                      │
│   source "$VENV/bin/activate"                                                │
│ fi                                                                           │
│ exec "$@"                                                                    │
│                                                                              │
│ container/run-job.sh (NEW, ~60 lines):                                       │
│ In-container job runner. Called from inside the container for managed        │
│ execution.                                                                   │
│ Activates venv, optionally sets SYGALDRY_IN_CONTAINER=1, runs command with   │
│ stdout/stderr                                                                │
│ captured to /repo/.zephyr-mlsys/logs/<job-name>.log if --log flag is set.    │
│                                                                              │
│ Generated Dockerfile uses COPY for these scripts (build context includes     │
│ them):                                                                       │
│ COPY container/entrypoint.sh /opt/mlsys-entrypoint.sh                        │
│ COPY container/run-job.sh    /opt/mlsys-run-job.sh                           │
│ RUN chmod +x /opt/mlsys-entrypoint.sh /opt/mlsys-run-job.sh                  │
│ ENV VIRTUAL_ENV=/opt/repo-venv                                               │
│ ENV PATH=/opt/repo-venv/bin:${PATH}                                          │
│ ENV MLSYS_VENV_PATH=/opt/repo-venv                                           │
│ ENTRYPOINT ["/opt/mlsys-entrypoint.sh"]                                      │
│                                                                              │
│ The Python helper copies container/entrypoint.sh and container/run-job.sh    │
│ from the                                                                     │
│ vendor kit source dir into the temp build context before docker build runs.  │
